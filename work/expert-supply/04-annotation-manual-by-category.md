# 04 分类标注说明书：试点三类写深，其余给模板

> 本文回答：法律检索、神经影像、建筑节能三类任务具体怎么写；其余类目的必填差异是什么；哪些类目首批不碰。
> 用法：先读 03 通用手册，再读本类目章节。通用规则不重复，这里只写“这一类特有的”。
> 原则：试点三类必须 Linux + CPU + 离线 + 资料可公开/合成；Windows、GPU、专有工具类目一律后排。

## 1. 法律检索与诉讼支持

### 1.1 典型工作流

| 工作流 | 输入 | 输出 | 难点 |
|---|---|---|---|
| 法规检索 memo | 一个事实场景 + 法规库 | 问题、结论、引证、风险 | 找对法条、判断现行有效、区分强制性/任意性 |
| 类案检索报告 | 争点 + 公开判决 | 类案表、裁判规则、分歧 | 同案判断、审级、地域、时间 |
| 合同条款审查 | 合同 + 业务背景 | 条款风险表、修改建议 | 识别实质风险，不是改错别字 |
| 诉讼时间线与争点表 | 合成案卷 | 时间线、争点、证据目录 | 事实与证据一一对应 |
| 证据目录整理 | 往来函、合同、付款凭证 | 证据清单、证明对象 | 关联性、真实性、合法性 |

不选：真实客户咨询、在办案件、需要出庭/发函、需要 Westlaw/Lexis 付费库、需要法院内部系统。

### 1.2 资料

- 公开：国家法律法规数据库、最高人民法院公报、公开裁判文书、地方人社局示范文本、公开仲裁案例。
- 合成：合同、解除通知、往来函、时间线、证据目录；用虚构公司名与人名。
- 禁止：客户合同、在办案卷、律师工作底稿、未公开和解协议、含真实当事人信息的判决全文（需匿名化）。

资料包至少含：1 份规范文本、1–3 份事实文件、1 份写作要求。每个文件标 `source_type`（statute/judgment/contract/synthetic）与 `effective_date`。

### 1.3 工具与环境

- 工具：浏览器（离线 HTML/PDF）、PDF 阅读器、Excel/CSV、Markdown/Word。无需法律数据库。
- 环境：Ubuntu 22.04，2 vCPU、4 GB RAM、5 GB 磁盘，完全离线。
- 不允许：把“登录某数据库”写进必跑步骤；如需付费库，任务必须提供已下载的公开替代件。

### 1.4 验证方式

| 检查 | 方法 | 失败示例 |
|---|---|---|
| 引证存在 | 在资料包内逐条匹配条号 | 引用第 39 条，原文只有 38 条 |
| 现行有效 | 对照 `effective_date` 与修订记录 | 引用已废止的 1994 年条例 |
| 引文准确 | 逐字比对，允许省略但不得改义 | 把“应当”写成“可以” |
| 争点—证据对应 | `issue_id` 在证据表与 memo 中都能找到 | 争点 3 无证据 |
| 日期一致 | 时间线与合同/函件日期核对 | 解除日早于送达日 |
| 匿名化 | 搜索真实姓名/公司/案号 | 出现真实案号 |

### 1.5 授权与伦理

- 只做法律信息整理，不提供正式法律意见；memo 里写“供内部研究，不构成法律意见”。
- 公开判决仍需匿名化；不得重新识别当事人。
- 合成案卷不得影射真实在办案件。
- 不得使用客户提供的保密文件；如专家自带，必须证明已获授权且可再分发。
- 引用规范要标版本与生效日期，避免“旧法新解”。

### 1.6 常见错误

1. 引用已废止/未生效的规范。
2. 条号对、款项错；把司法解释当法律。
3. 把判决中的“本院认为”当唯一规则，忽略审级与地域。
4. 事实与结论之间缺“涵摄”步骤。
5. memo 写成普法文章，没有回答具体问题。
6. 出现真实当事人、案号、律师姓名。
7. 成功标准写“结论正确”，不可检查。
8. 任务需要付费数据库，环境不可复现。

### 1.7 必填字段差异

| 字段 | 额外要求 |
|---|---|
| identity | `legal_jurisdiction`、`legal_domain`、`source_type` |
| materials | 每份规范标 `effective_date`、`issuing_body`；每份判决标 `court_level`、`anonymized` |
| operations | 必须含“定位规范—核对现行有效—涵摄—引证—风险标注”五步 |
| success_criteria | 至少 1 条“引证可回溯”，1 条“匿名化”，1 条“争点—证据对应” |
| provenance | 规范版本、访问日期、判决来源、匿名化方法 |
| review | 必须问“换一个法条/审级，结论是否改变” |

### 1.8 样例任务提纲

**标题**：依据《劳动合同法》第 39、40 条，对 3 份解除通知做合法性检索并出具引证 memo

- 角色：制造企业法务专员；期限：周五前；约束：只出内部 memo，不对外发函。
- 资料：M1 法条摘录（含生效日期）、M2 三份合成解除通知、M3 员工手册条款、M4 合成考勤记录。
- 步骤：抽取事实 → 匹配第 39/40 条 → 判断程序与实体 → 标注 2 处需外部律师确认 → 写 memo + 引证表。
- 交付：`memo.md`、`citations.csv`、`risks.csv`。
- 成功：每条结论有现行法条；3 份通知逐一分析；引证表可回溯；无真实信息；风险分级合理。
- 评审问题：如果员工手册未公示，第 39 条适用是否改变？

### 1.9 分类检查表

- [ ] 规范现行有效，条号/款项准确
- [ ] 事实—规范—结论三段齐全
- [ ] 引证表能回溯到资料包
- [ ] 争点与证据一一对应
- [ ] 日期链无矛盾
- [ ] 全匿名
- [ ] 不构成正式法律意见
- [ ] 无需付费数据库
- [ ] 成功标准可逐条检查

## 2. 神经影像数据整理与预处理

### 2.1 典型工作流

| 工作流 | 输入 | 输出 | 难点 |
|---|---|---|---|
| DICOM→BIDS | 3–5 个序列 | BIDS 目录、侧车 JSON | 命名、字段、方向 |
| 去脸与质控 | 结构像 | 去脸影像、QC 图 | 只处理一张切片会失败 |
| 预处理报告 | BIDS 数据 | 报告、参数表、异常清单 | 参数与报告一致 |
| 数据 curation | 多受试者导出 | `participants.tsv`、数据集描述 | 字段映射、缺失值 |
| 运动质控 | fMRI 时间序列 | 位移指标、剔除建议 | 阈值与判断 |

不选：真实患者影像、需要 IRB 的新采集、需要 GPU 的大规模 fMRIPrep、需要医院 PACS 的流程。试点只做“数据整理 + 轻量质控”。

### 2.2 资料

- 公开：OpenNeuro（CC0/CC-BY）、BIDS 示例数据集、MRI  phantom。
- 合成：用 `mri_synthstrip`/phantom 生成的 DICOM；伪造 `participants.tsv`，姓名用 `sub-01`。
- 禁止：未脱敏 DICOM、含面部特征的原图、含生日/ID 的 header、受控访问数据、需要数据使用协议的队列。

资料包至少含：DICOM 目录、受试者表、BIDS 规范摘要、期望输出示例（不能是答案）。

### 2.3 工具与环境

- 工具：`dcm2niix`、`bids-validator`、FSL（`fslhd`、`fsleyes` 可选）、Python（`pydicom`、`nibabel`、`pandas`）。
- 环境：Ubuntu 22.04，4 vCPU、8 GB RAM、20 GB 磁盘，离线；无 GPU、无 GUI 必跑。
- 版本写死，例如 `dcm2niix 1.0.20240202`、`bids-validator 1.14.6`；不写“最新版”。

### 2.4 验证方式

| 检查 | 方法 | 失败示例 |
|---|---|---|
| BIDS 结构 | `bids-validator` 退出码 0 | 文件名 `T1.nii` |
| 侧车字段 | 逐字段核对 JSON | 缺 `RepetitionTime` |
| 身份信息 | `grep` header + 人工看 | JSON 里有 `PatientName` |
| 去脸 | 看 3 个平面 + 边缘 | 只模糊一张切片 |
| 方向/单位 | `fslhd` 看 qform/sform、pixdim | 左右翻转、TR 单位错 |
| 行数一致 | `participants.tsv` 与目录逐行 | 12 人只有 11 行 |
| QC 覆盖 | 每受试者×序列一行 | 缺 T2 |

### 2.5 授权与伦理

- 只用合成或公开可再分发数据；公开数据也要查许可是否允许商用/再分发。
- 去脸不是“打码”，要处理面部与耳部；保留可逆性说明。
- 不上传原始 DICOM；不把 header 里的机构名、设备序列号带出。
- 涉及患者数据一律拒绝；需要 IRB 的任务首批不做。
- 报告里写“仅用于方法学演示，不用于临床诊断”。

### 2.6 常见错误

1. 文件名符合 BIDS，但 JSON 字段缺失或单位错。
2. 只去脸一层，矢状面仍可识别。
3. `participants.tsv` 与目录不一致。
4. 转换命令没记录版本，无法复现。
5. 把 `dcm2niix` 的默认输出直接当 BIDS，没重命名。
6. 用 GPU 版 fMRIPrep 做必跑步骤，环境不可复现。
7. 报告写“预处理完成”，没有参数与异常清单。
8. 把受控数据写成公开。

### 2.7 必填字段差异

| 字段 | 额外要求 |
|---|---|
| identity | `modality`（MRI/CT/PET）、`species`、`bids_version` |
| materials | DICOM 序列清单、受试者表、许可、去标识方法 |
| operations | 转换命令、重命名规则、validator 命令、QC 步骤 |
| environment | 工具版本、磁盘、是否 GUI/GPU |
| success_criteria | validator 退出码、字段清单、PHI 扫描、QC 覆盖 |
| provenance | 数据来源、许可、去标识方法、下载日期 |
| review | 必须问“validator 通过但字段错误怎么发现” |

### 2.8 样例任务提纲

**标题**：将 3 个 DICOM 序列转换为 BIDS 并修复 4 类侧车字段错误

- 角色：影像核心实验室数据工程师；期限：周一前；约束：不上传原始 DICOM，不带身份信息。
- 资料：M1 合成 DICOM（T1w、T2w、rest）、M2 受试者表、M3 BIDS 规范摘要。
- 步骤：`dcm2niix` 转换 → 重命名 → 补 JSON → `bids-validator` → 去脸/QC → 写报告。
- 交付：`bids/`、`qc.csv`、`logs/`、`report.md`。
- 成功：validator 0 error；3 序列字段齐全；无 PHI；QC 覆盖 3×3；命令可复现。
- 评审问题：如果 TR 在 DICOM 与 JSON 中不一致，以哪个为准？为什么？

### 2.9 分类检查表

- [ ] 数据是合成/公开且许可允许
- [ ] DICOM 无真实身份信息
- [ ] BIDS 命名与 JSON 字段齐全
- [ ] validator 退出码 0
- [ ] 去脸覆盖三个平面
- [ ] `participants.tsv` 行数一致
- [ ] 工具版本与命令已记录
- [ ] 无 GPU/Windows 必跑依赖
- [ ] 报告含异常清单与限制

## 3. 建筑节能建模与 M&V

### 3.1 典型工作流

| 工作流 | 输入 | 输出 | 难点 |
|---|---|---|---|
| 基线能耗模型 | 建筑几何、HVAC、气象 | 基线模型、校准报告 | 边界、单位、校准 |
| 节能措施评估 | 基线模型 + ECM 参数 | 节能量、成本、敏感性 | 同气象、同边界 |
| M&V 方案 | 账单、表计、基线 | M&V 计划、节能量表 | 选项 A/B/C/D 选择 |
| 围护结构权衡 | 墙体/窗/遮阳 | 负荷与能耗对比 | 传热系数、太阳得热 |
| HVAC 控制策略 |  schedules、设定点 | 控制前后对比 | 同时调整多个变量 |

不选：需要业主账单、需要现场审计、需要 Windows 版 DesignBuilder/IES、需要 GPU 的大规模 CFD。首批用 EnergyPlus 示例模型 + 公开气象 + 合成账单。

### 3.2 资料

- 公开：EnergyPlus 示例模型（`5ZoneAirCooled.idf` 等）、TMY3 气象、ASHRAE 90.1/62.1 的公开摘要（注意版权，不整本复制）。
- 合成：电费/燃气账单、入住率、设备清单、改造前后读数。
- 禁止：业主未授权能耗、电网原始数据、商业软件许可文件、整本受版权保护的标准。

资料包至少含：IDF 模型、天气文件、12 个月合成账单、改造说明、边界定义。

### 3.3 工具与环境

- 工具：EnergyPlus（CLI）、OpenStudio CLI（可选）、Python（`eppy`/`pandas`）、Excel。
- 环境：Ubuntu 22.04，4 vCPU、8 GB RAM、20 GB 磁盘，离线；无 GUI 必跑；EnergyPlus 版本写死（如 24.1.0）。
- 运行时间：示例模型 <5 分钟；全年逐时 <15 分钟。

### 3.4 验证方式

| 检查 | 方法 | 失败示例 |
|---|---|---|
| 能量平衡 | 逐时/逐月供需平衡 | 冷负荷 > 总能耗 |
| 单位一致 | kWh、kBtu、therm 统一 | 混用 kWh 与 kBtu |
| 边界一致 | 基线/改造面积、系统相同 | 改造后面积多了 10% |
| 气象一致 | 同一 EPW | 基线用北京、改造用上海 |
| 节能量 | `baseline - measure` 可重算 | 直接引用厂商数字 |
| 校准 | 月度 CV(RMSE)、NMBE（假设 ≤15%、±5%，待评审确认） | 未校准就说“吻合” |
| 账单核对 | 合成账单与模拟逐月对比 | 12 个月只对 1 个月 |

### 3.5 授权与伦理

- 账单与能耗数据必须业主书面同意，或用合成数据；首批只用合成。
- 气象与示例模型是公开的，但仍要标版次与来源。
- 标准文本只引用必要条款，不复制整本。
- 结论写“基于模型与假设”，不承诺实际节费。
- 涉及补贴/碳核算时，标明口径与边界。

### 3.6 常见错误

1. 基线/改造用不同气象或不同面积。
2. 单位混用，节能量差 3.4 倍。
3. 只改一个参数，却声称整体节能。
4. 未校准就报节能量。
5. 账单是年度总表，却做月度校准。
6. 把“设备额定效率”当实际运行效率。
7. M&V 选项与数据条件不匹配。
8. 成功标准写“节能 20%”，没写边界与气象。

### 3.7 必填字段差异

| 字段 | 额外要求 |
|---|---|
| identity | `building_type`、`climate_zone`、`mv_option` |
| materials | IDF/EPW 版本、账单周期、面积、边界 |
| operations | 模拟命令、校准步骤、节能量计算 |
| environment | EnergyPlus 版本、天气文件、运行时间 |
| success_criteria | 能量平衡、单位、边界、校准阈值、可重算 |
| provenance | 模型来源、气象来源、账单合成说明 |
| review | 必须问“换一个气象年，结论是否稳定” |

### 3.8 样例任务提纲

**标题**：用 EnergyPlus 示例模型评估外墙保温改造的节能量并给出 M&V 方案

- 角色：节能咨询公司分析师；期限：两周；约束：只用公开模型与合成账单，不承诺实际节费。
- 资料：M1 `5ZoneAirCooled.idf`、M2 北京 TMY3、M3 12 个月合成电费、M4 改造说明（外墙 U 值 0.6→0.35）。
- 步骤：跑基线 → 校准账单 → 改外墙 → 同气象重跑 → 算节能量 → 写 M&V 选项与不确定性。
- 交付：`baseline.csv`、`measure.csv`、`savings.csv`、`mv_plan.md`、`model/`。
- 成功：基线/改造同气象同面积；单位统一 kWh；节能量可重算；校准指标达标；M&V 选项有理由。
- 评审问题：如果入住率从 0.8 降到 0.6，节能量如何归因？

### 3.9 分类检查表

- [ ] 模型与气象版本写死
- [ ] 基线/改造边界一致
- [ ] 单位统一
- [ ] 账单与模拟逐月核对
- [ ] 校准指标可复算
- [ ] 节能量 = 基线 − 改造
- [ ] M&V 选项与数据匹配
- [ ] 无业主未授权数据
- [ ] 结论含假设与限制

## 5. 试点不碰的类目与原因

| 类目/工作流 | 依赖 | 为什么试点不碰 | 什么时候做 |
|---|---|---|---|
| 无障碍（NVDA/JAWS） | Windows + 读屏软件 | 环境不可离线复现，P5 明确放后 | B4，Windows 决策后 |
| 3D 动画/渲染 | GPU、Maya/Blender GUI | 渲染时间与许可证不可控 | B4，CPU 渲染可行后 |
| 音频后期 | Pro Tools/许可证 | 插件与音频接口依赖 | B4，用 Audacity 替代后 |
| 医学影像分割（Slicer GUI） | GUI、GPU、大模型 | 8 GiB 级资产与 GUI | B3 之后，需工程评估 |
| 半导体 EDA | 商业 EDA、许可证 | 商业工具许可不可转；B3 只做开源 RTL 仿真/合成网表 | 试点不碰；B3/B4 的 4 条半导体配额用开源替代，不能替代则换题 |
| 航空/海事 | Windows 专用软件、专有数据 | 零覆盖 + 高授权风险 | 暂不做 |
| 化工/采矿 | 工艺模拟器、现场数据 | 零覆盖 + 安全风险 | 暂不做 |
| 教育技术 | LMS 平台、Windows | 零覆盖 + 平台依赖 | 暂不做 |
| 精准农业 | 农机数据、专有格式 | 零覆盖 + 数据不可得 | 暂不做 |

## 6. 自检

- 试点三类都有：典型工作流、资料、工具、环境、验证、授权、常见错误、必填差异、样例、检查表。
- 其余 10 域只给模板与要点，没有平均展开。
- 所有“首批不碰”的类目都写了依赖与解除条件。
- 三类样例都不含真实患者、客户、案卷、业主数据。
