# 05 官方完整包：唯一完整样例

> 本文只把 `legal_dr_fees_01` 当完整样例。三份角色材料是迁移练习，不是完整样例，也不是提交模板。
> 读法：先读 `02a-ale-context-and-data.md` 第 1 到 6 节，再读本文第 0 节，掌握完整包的结构和分离方式；然后用第 1 节把结构迁移到自己的领域。正式生产按 02a 的官方标准执行：合同对齐、保留工作、可离线复现；不设固定步数或材料数。
> 三份练习对应 3 条试点。法律 42 条走供应方 ALE-data 导入，不在专家手册里做全流程样例；供应方包检查见 `04` 第 1 节和本文附录。
> 全部使用公开或合成资料，不复制官方任务正文、隐藏评分规则或受限资产。

## 0. 先看官方完整包

官方数据包是唯一完整样例来源。`inputs/frozen/03_ale-data/task-data-v1.1/legal/legal_dr_fees_01/base` 是其中一条，1.0M，包含 7 份 PDF、5 个案件、1 份金标、1 份验证记录。

它不是唯一形态。官方 122 条任务的输入中位 7 份，p90 85 份，规模差异很大，见 `02a` 第 3.7 节。用这条看输入、输出、答案、评分和验证怎么分开，不要套目录。

### 0.1 包的完整结构

```
base/
  input/
    task_brief.md
    output_contract.json
    document_manifest.json
    cases.json
    documents/
      bac_*.pdf                7 份
    runtime_env/
      pyproject.toml
  reference/
    answer_key.json
    stage1_manifest.json
  software/
    README.txt
    python3.12
```

### 0.2 每个文件做什么

| 文件 | 作用 | 关键点 |
|---|---|---|
| `input/task_brief.md` | 任务说明 | 闭卷；只允许用 `base/input` 下的材料；5 个案件；交付一个 JSON；字段名和两位小数写死 |
| `input/output_contract.json` | 输出合同 | 根对象、`cases` 数组、case_1 到 case_5、字段类型、示例形状 |
| `input/document_manifest.json` | 材料清单 | 7 份 PDF 的 document_id、文件名、格式、相对路径、sha256 |
| `input/cases.json` | 案件事实 | 5 个案件的金额和 special_condition；case_4 已达成和解 |
| `input/documents/` | 源材料 | 7 份真实形态的 BAC PDF，不是整理后的表格 |
| `input/runtime_env/pyproject.toml` | 运行环境 | 任务需要的 Python 依赖 |
| `reference/answer_key.json` | 金标 | 5 案三字段答案；三项权重 7/7/6；容差 0.01 元 |
| `reference/stage1_manifest.json` | 验证记录 | 正例 1.0、负例 0.0、满分 100；输入泄漏审查结论 |
| `software/` | 运行软件 | 任务运行需要的解释器或工具说明 |

### 0.3 任务说明写到什么程度

`task_brief.md` 只写 Agent 需要知道的四件事。

1. 场景和角色。你在什么机构，处理什么案件。
2. 输入范围。只能读 `base/input` 下的材料，闭卷。
3. 要做什么。对 5 个案件计算机构费和仲裁员报酬。
4. 交付什么。写到 `output/arbitration_fee_results.json`，字段名和两位小数写死。

它不写“先读哪份 PDF，再算什么”，也不给公式答案。步骤由 Agent 自己规划，判断由 Agent 自己做。这是 ALE 任务和“操作手册”的区别。

### 0.4 输出合同写到什么程度

`output_contract.json` 把交付物写死到机器能校验。

- 根对象必须有 `cases`。
- `cases` 是数组，长度 5。
- 每个元素有 `case_id`、`institution_fee_rmb`、`arbitrator_remuneration_rmb`、`total_fee_rmb`。
- 金额是数字，保留两位小数。
- 示例形状给出一个合法对象。

专家写任务源时，`deliverables` 块就要写到这个程度。不是“一份 JSON”，而是路径、字段、类型、精度、示例。

### 0.5 金标和验证怎么分开

`reference/answer_key.json` 写答案、权重和容差。它不在 `input/` 里，Agent 看不到。

`reference/stage1_manifest.json` 写验证结果。正例得分 1.0，负例得分 0.0，满分 100。它还写输入泄漏审查结论。

> input contains source PDFs, case facts, output schema, and runtime manifest only; no gold fee values or scoring code.

这句话是标准动作。提交前要自己检查一遍。输入里不能有答案、评分代码、金标痕迹。

### 0.6 这份包为什么是合格任务

- 有真实材料。7 份 PDF，不是一段编造的案例。
- 有真实摩擦。案件事实、金额、和解条件分散在多份文件里，需要交叉核对。
- 有多步判断。先读任务，再读案件，再找费率规则，再算机构费和报酬，再检查总额。
- 有精确交付物。一个 JSON，5 个案件，4 个字段，两位小数。
- 有可复现判定。答案、权重、容差、正负 fixture 都写死。
- 有泄漏审查。输入和答案分开。

### 0.7 映射到我们的十块任务源

| 官方包 | 作用 | 我们的十块 | 工程 Harbor 包 |
|---|---|---|---|
| `task_brief.md` | 指令和约束 | identity + scenario | `instruction.md` |
| `documents/` + `document_manifest.json` + `cases.json` | 输入和事实 | materials | `input/` 或 environment 挂载 |
| `output_contract.json` | 交付物合同 | deliverables | `instruction.md` 的 artifacts 段 + 验证器 |
| `answer_key.json` | 金标、权重、容差 | success_criteria + review | `solution/` + `tests/` |
| `runtime_env/` + `software/` | 环境 | environment | `environment/` |
| `stage1_manifest.json` | 验证与泄漏审查 | review + provenance | `tests/` + `metadata` |

### 0.8 映射到 Harbor 包

工程最终会把你的任务源转成 Harbor 1.4 + ALE 扩展格式。

| Harbor 文件 | 从哪来 | 谁写 |
|---|---|---|
| `task.toml` | 环境、超时、artifacts、验证器配置 | 工程 |
| `instruction.md` | 你的 scenario + 交付物要求 | 工程基于你的任务源定稿 |
| `input/` | 你的 materials | 工程打包 |
| `environment/` | 你的 environment | 工程 |
| `tests/` | 你的 success_criteria | 工程写验证器 |
| `solution/` | 你的金标答案 | 工程封装 |

专家不写这些文件。专家要把十块写到工程能直接转的程度。

### 0.9 不要照抄什么

- 不要照抄法律内容、案件金额、费率规则。
- 不要照抄官方任务的正文、答案或评分代码。
- 不要以为每条任务都必须长成法律任务。结构和分离方式要学，领域内容要是你自己的。
- 不要用简化的小数据替代真实材料。第 1 节三份练习只用于迁移结构，不是完整样例，不能照抄长度和材料数量。

## 1. 三份迁移练习

> 练习不是完整样例。每份只给任务种子、材料、判断点、交付物、成功标准、常见失败。你要按第 0 节扩成完整任务：合同对齐、保留工作、可离线复现；步数和材料数由工作决定，不设固定门槛。

### 1.1 商业会计

**任务种子。** 两家同行业制造业公司 2022 到 2024 年公开年报，加一份合成总账，做收入与应收勾稽、12 个科目核对、3 条异常识别。

| 项 | 练习 | 正式生产要补 |
|---|---|---|
| 材料 | 2 份年报、2 份附注、总账、行业基准、邮件、上年底稿，共 6-7 份 | 按工作需要补合同、发票、银行流水、纳税申报、关联方清单；官方商业任务输入中位 7 份，不要为凑数加 |
| 核心判断 | 合并范围、收入确认、期间与单位、应收与合同负债、非经常损益 | 写清每个判断的依据、页码、口径 |
| 交付物 | `reconciliation.xlsx`、`memo.md`、`evidence_index.csv` | 精确文件名、列名、格式、两位小数 |
| 成功标准 | 12 个科目差额为 0；3 条异常各有页码或凭证；不提供投资建议 | 每条指令要求至少一条可检查标准，数值带容差；数量由要求决定 |
| 常见失败 | 把增长当质量；总账太干净；异常没有来源；只写结论不写步骤 | 模型轻易做完，说明太简单 |

**怎么扩成完整任务。** 先补真实形态材料（合同、发票、银行流水、纳税申报），再把练习扩成完整工作流：定范围、读附注、做勾稽、查异常、追凭证、写 memo、做自检。步数由工作决定，不要为凑数加无关操作。最后让模型只凭任务说明和输入试做，记录耗时、得分和错误类型。

### 1.2 神经影像

**任务种子。** 5 名被试的公开 DICOM，转成 BIDS 目录，处理 4 类常见错误，写质量报告。

| 项 | 练习 | 正式生产要补 |
|---|---|---|
| 材料 | DICOM、`participants.tsv`、`dataset_description.json`、validator 输出、sidecar 模板、实验室 SOP、邮件，共 7 份 | 按工作需要补知情同意或 IRB 记录、扫描参数、去标识记录、defacing 日志；影像数据可以很大，按 02a 的资产规则处理 |
| 核心判断 | 字段来源、方向约定、去标识边界、元数据保留、失败处理 | 写清 DICOM 头字段到 BIDS 字段的映射 |
| 交付物 | `bids/`、`qc.csv`、`validator.log`、`methods.md` | 精确目录、文件名、JSON 字段、日志格式 |
| 成功标准 | validator 0 error；无直接标识符；sidecar 字段完整；QC 覆盖全部被试 | 每条指令要求至少一条，含失败重跑与证据位置；数量由要求决定 |
| 常见失败 | 只改文件名；不做去标识检查；没有 provenance；把 validator 警告当通过 | 模型试做时只给 DICOM 和任务说明，看它能否自己发现错误 |

**怎么扩成完整任务。** 加同意书、扫描参数、去标识记录、defacing 日志，材料数量按工作需要。把练习扩成完整工作流：盘点、映射、转换、校验、修复、复跑、写报告、自检。至少保留 3 类真实错误，不要把所有文件整理成理想状态。

### 1.3 建筑节能

**任务种子。** 一栋公开或合成建筑的 12 个月电费、燃气账单和气象数据，用 EnergyPlus 做基线校准，再评估一项改造的节能量。

| 项 | 练习 | 正式生产要补 |
|---|---|---|
| 材料 | 示例模型、12 个月账单、气象文件、电表数据、ASHRAE 14、电价文件、上一年审计，共 7 份 | 按工作需要补图纸、设备表、运行记录、调试报告、入住率；官方工程任务输入中位 9 份 |
| 核心判断 | 建筑边界、用能系统、单位换算、校准口径、节能基线 | 写清边界、计量点、账单期间、天气修正 |
| 交付物 | 模型文件、`calibration.csv`、`report.md`、`evidence_index.csv` | 精确文件名、列名、单位、报告章节 |
| 成功标准 | CVRMSE ≤15%；NMBE ≤5%；节能量可复算；不确定性写清 | 每条指令要求至少一条，含容差和证据位置；数量由要求决定 |
| 常见失败 | 边界不一致；单位错；用改造后账单做基线；只报一个节能量，不写不确定性 | 模型试做时看它会不会直接相信账单 |

**怎么扩成完整任务。** 加图纸、设备表、运行记录、调试报告、入住率，材料数量按工作需要。把练习扩成完整工作流：定边界、读账单、建模型、校准、诊断、算节能、做不确定性、写报告、自检。保留账单缺月、单位混用、入住率变化等真实摩擦。

### 1.4 三份练习的共同点

| 练习 | 核心判断 | 证据 | 最常见失败 | 扩成完整任务先加什么 |
|---|---|---|---|---|
| 商业会计 | 收入确认与应收质量 | 页码、凭证、科目余额 | 把增长当质量 | 合同、发票、流水、纳税申报 |
| 神经影像 | 字段映射与去标识 | DICOM 头、validator 日志、QC 表 | 只改文件名 | 同意书、扫描参数、去标识记录 |
| 建筑节能 | 边界、单位、基线 | 账单、气象、模型输出、调试记录 | 边界不一致 | 图纸、设备表、运行记录、入住率 |

三份练习只到 5-12 步、5-7 份材料。正式任务的大小由工作决定；官方 122 条中输入中位 7 份，p90 85 份，1 份的也有 11 条。练习用于把第 0 节的结构迁移到自己的领域，不是提交模板，也不是难度上限。

## 附录：法律供应方包检查（不占试点位）

法律 42 条不经过专家任务源、评审和冻结全流程，由供应方按 ALE-data 提供，走 `import -> 基础校验 -> 转 Harbor`。专家手册不要求写法律任务源；本节只给平台和工程做供应方包检查。

- 包结构：`base/input/task_brief.md`、`output_contract.json`、`document_manifest.json`、`cases.json`、`documents/`、`runtime_env/`。
- 基础校验：文件存在、JSON 可解析、引用路径可解析、哈希与清单一致、无真实当事人信息。
- 内容抽检：按 `04` 第 1 节的引证、程序、匿名化、争点—证据对应检查；基础校验过不了内容审核。
- 供应方仍要出专业背书、资料授权与脱敏说明；合作方接受供应方包才计入 500。
