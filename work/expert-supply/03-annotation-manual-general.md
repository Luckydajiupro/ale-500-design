# 03 通用标注说明书：给专家，不给工程师

> 本文回答：一条合格的 ALE 任务长什么样；十块字段各写什么；哪些写法一定会被退回；提交前怎么自检。
> 读者：签约专家、领域评审、专家运营。读者不需要会 Docker、Python 或验证器。
> 底线：你写的是“另一个人拿着一包资料能重做一遍的专业工作”，不是经验分享，也不是问答。

## 1. 三个基本要求

1. **可重做**：换一个同专业的人，只看你的任务包，能做出同样的交付物。
2. **可判定**：成功与否靠文件、字段、阈值、引用，不靠“我觉得好”。
3. **可授权**：资料是公开的、合成的，或你明确有权使用的；不碰患者、客户、案卷、业主原始数据。

## 2. 任务 anatomy：七件事与十块

一条任务必须同时有七件事：

| 七件事 | 说明 | 对应十块 |
|---|---|---|
| 任务陈述 | 一句话说清要做什么 | identity + scenario |
| 源资料 | 输入文件、数据、文献、截图 | materials |
| 输入文件 | 可打开、可校验的具体文件 | materials |
| 环境 | 操作系统、软件、依赖、是否离线 | environment |
| 可执行的多步操作 | 不是一步问答，而是有顺序的工作流 | operations |
| 预期交付物 | 文件、表、图、代码、报告 | deliverables |
| 成功判定 | 可检查的标准与证据 | success_criteria + review |

十块是平台字段，不是写作提纲。顺序可以调整，但十块都不能空。

| 块 | 一句话 | 常见字数 |
|---|---|---:|
| identity | 这是谁、在什么场景、要交付什么 | 80–200 字 |
| scenario | 背景、角色、目标、约束、时间 | 200–500 字 |
| materials | 文件清单、来源、授权、哈希 | 表格 |
| operations | 步骤、工具、参数、判断点 | 5–12 步 |
| deliverables | 文件路径、格式、字段、命名 | 表格 |
| success_criteria | 可检查的通过条件 | 5–10 条 |
| environment | OS、软件、版本、资源、网络 | 表格 |
| review | 风险、评审问题、需人工看什么 | 5–10 条 |
| provenance | 来源、日期、作者、许可、脱敏 | 表格 |
| handoff | 交接包、已知限制、未决项 | 清单 |

## 3. 什么算合格，什么不算

| 合格 | 不合格 |
|---|---|
| 有真实职业角色与交付压力 | “请介绍一下……” |
| 资料是具体文件，能打开 | “参考相关文献” |
| 步骤有顺序、有判断点 | 一步“分析并给出结论” |
| 交付物有路径、格式、字段 | “一份报告” |
| 成功标准可逐条检查 | “专业、准确、完整” |
| 失败模式可预期 | 只有唯一答案，没有过程 |
| 资料授权清楚 | “网上找的” |
| 环境可复现 | “有电脑就行” |

一个快速测试：把任务发给同专业但没做过这条的同事，问他三个问题——你知道先做什么吗？你知道做到什么程度算完吗？你能判断自己做得对不对吗？三个都是“能”，才合格。

## 4. 怎么选真实工作流

好的工作流有五个特征：

1. 你过去 12 个月亲手做过至少 2 次。
2. 有明确的输入和输出，不是无限开放的咨询。
3. 中间有 2–3 个需要专业判断的分支。
4. 失败会留下痕迹（错引、错单位、错阈值、错版本）。
5. 资料能公开或合成，不依赖客户/患者/案卷。

不要选：一次性的战略建议、需要现场走访的调研、纯创意、纯聊天、需要实时外部服务的流程。

选完后写一句“这条任务的专业难点是什么”。写不出，说明工作流太浅。

## 5. identity：标题要能检索，不要口号

**必须写**：任务编号、中文标题、英文标题、专业领域、子域、任务族、难度、预计工时、交付物类型。

合格例 1：
> `LEGAL-RES-014` 依据现行《劳动合同法》第 39 条，对 3 份解除通知做合法性检索并出具引证 memo

合格例 2：
> `NEURO-BIDS-007` 将 3 个 DICOM 序列转换为 BIDS 结构并修复 4 类侧车字段错误

不合格例 1：
> 法律任务 1

不合格例 2：
> 神经影像数据处理（没有说明输入、输出、难点）

常见错误：标题写成“关于……的思考”；难度与工时明显不匹配；英文标题机翻。

## 6. scenario：写清角色、目标、约束、时间

**必须写**：你是谁、为谁做、为什么要做、期限、不能做什么、交付给谁。

合格例 1：
> 你是某中型制造企业的法务专员。销售总监要求在周五前判断 3 份区域经销合同中的“最低转售价格”条款是否违反现行反垄断规定。你不能对外发函，只能出具内部 memo，引用现行有效规范，并标注 2 处需要外部律师确认的风险。

合格例 2：
> 你是影像核心实验室的数据工程师。PI 下周一要上传 12 名受试者的静息态数据到公开仓库，但现有导出目录命名不一致、缺少 JSON 侧车。你需要在不上传原始身份信息的前提下，整理成 BIDS 并给出质控清单。

不合格例 1：
> 你是一名专家，请分析这份合同。

不合格例 2：
> 请处理这些影像数据，越快越好。

常见错误：角色与交付物不匹配；没有期限；把“约束”写成“注意事项”；背景里塞入与任务无关的公司史。

## 7. materials：每个文件都能被找到、打开、校验

**必须写**：文件 ID、文件名、类型、大小、来源、许可/授权状态、SHA-256、是否脱敏、放在哪个目录。

合格例 1：

| id | 文件 | 来源 | 许可 | 用途 |
|---|---|---|---|---|
| M1 | `labor_contract_2024.pdf` | 公开示范文本（人社局网站） | 政府公开 | 条款比对 |
| M2 | `termination_notice_A.docx` | 合成 | 项目自制 | 事实基础 |
| M3 | `statute_excerpt.md` | 官方法规库 | 公共领域 | 引证 |

合格例 2：

| id | 文件 | 来源 | 许可 | 用途 |
|---|---|---|---|---|
| M1 | `sub-01_T1w.nii.gz` | 合成 Phantom | CC0 | 结构像 |
| M2 | `participants.tsv` | 合成 | 项目自制 | 受试者表 |
| M3 | `dcm2niix.log` | 工具输出 | 项目自制 | 转换证据 |

不合格例 1：
> 资料：网上找的合同模板。

不合格例 2：
> 资料：一些影像数据（没有文件名、没有授权、没有哈希）。

常见错误：只写“公开数据”不写具体 URL/版本；把受控数据写成公开；文件改名后哈希没更新；缺少“这个文件用来干什么”。

## 8. operations：步骤要有顺序、工具、参数、判断点

**必须写**：每一步做什么、用什么工具/版本、关键参数、看到什么算通过、失败怎么办。

合格例 1：
1. 用 `pdftotext -layout` 抽取 M1 全文，保存 `work/M1.txt`；检查页数与原文一致。
2. 在 M1 中定位第 39 条，记录条号、生效日期、修订记录。
3. 对 M2 的 3 份通知逐份标注“事实—条款—结论”，写入 `work/analysis.csv`。
4. 对每条结论给出至少 1 个规范引用和 1 个反例；无引用则标 `NEED_REVIEW`。
5. 汇总为 memo，引用格式 `《法名》第 X 条第 Y 款`。

合格例 2：
1. 用 `dcm2niix -b y -z y -o raw/` 转换 3 个序列；记录版本与命令。
2. 按 BIDS 规范重命名 `sub-01_ses-01_T1w.nii.gz` 等；检查 4 个必需 JSON 字段。
3. 运行 `bids-validator`，保存完整输出。
4. 对 validator 的每个 error 写修复动作；warning 写是否接受及理由。
5. 生成 `participants.tsv`，字段与源表逐行核对。

不合格例 1：
> 分析合同并得出结论。

不合格例 2：
> 用软件处理一下影像。

常见错误：把“判断”写成“看一下”；参数缺失；没有失败分支；步骤顺序颠倒；把工程侧的 Docker 命令写进来（专家不需要）。

## 9. deliverables：路径、格式、字段、命名

**必须写**：交付什么文件、放在哪、什么格式、有哪些列/章节、命名规则、编码。

合格例 1：

| 交付物 | 路径 | 格式 | 必需内容 |
|---|---|---|---|
| 检索 memo | `output/memo.md` | Markdown | 问题、结论、引证、风险 |
| 引证表 | `output/citations.csv` | CSV UTF-8 | `claim_id,source,article,effective_date,url` |
| 风险清单 | `output/risks.csv` | CSV | `risk_id,level,description,owner` |

合格例 2：

| 交付物 | 路径 | 格式 | 必需内容 |
|---|---|---|---|
| BIDS 目录 | `output/bids/` | 目录 | 3 个序列、participants.tsv、dataset_description.json |
| 转换日志 | `output/logs/dcm2niix.log` | 文本 | 命令、版本、每序列结果 |
| 质控表 | `output/qc.csv` | CSV | `subject,series,check,status,note` |

不合格例 1：
> 交付一份报告。

不合格例 2：
> 交付处理后的数据。

常见错误：路径用绝对路径；CSV 列名中英混用；没有编码；交付物与 success_criteria 不对应。

## 10. success_criteria：每条都能被第三人检查

**必须写**：通过条件、阈值、检查方法、证据位置、什么算失败。

合格例 1：
- 每条结论至少 1 个现行有效规范引用；引用条号与原文一致。
- 3 份通知的“事实—条款—结论”三段齐全，缺一段即失败。
- `citations.csv` 的 `url` 可访问，`effective_date` 不晚于任务日期。
- memo 中不出现真实当事人姓名；出现即失败。

合格例 2：
- `bids-validator` 退出码为 0；有 error 即失败。
- 3 个序列的文件名、JSON 字段与 `participants.tsv` 一致；逐行核对。
- 无原始 DICOM 中的姓名、ID、生日；出现即失败。
- `qc.csv` 覆盖每个受试者×序列，缺行即失败。

不合格例 1：
> 报告专业、准确、完整。

不合格例 2：
> 数据整理正确。

常见错误：用形容词；阈值不可测；把“评审喜欢”写进标准；成功标准与交付物数量不一致。

## 11. environment：写清能不能离线、要不要 GUI/GPU

**必须写**：OS、架构、CPU/内存/磁盘、软件与版本、依赖安装方式、网络要求、是否需要 GUI/GPU/Windows、预计运行时间。

合格例 1：
> Ubuntu 22.04 / x86_64；4 vCPU、8 GB RAM、20 GB 磁盘；Python 3.11、pandas 2.2、pypdf 4.2；完全离线；无需 GUI/GPU；预计 10 分钟。

合格例 2：
> Linux x86_64；8 vCPU、16 GB RAM、50 GB 磁盘；FSL 6.0.7、dcm2niix 1.0.2024；离线；无 GUI；fMRIPrep 可选但不在必跑路径；预计 25 分钟。

不合格例 1：
> 有电脑就行。

不合格例 2：
> 需要 GPU（没说什么卡、什么驱动、什么版本）。

常见错误：写“最新版”；依赖需要联网安装；把 Windows 软件写成 Linux；磁盘估算明显不足。

## 12. review：告诉评审该看什么

**必须写**：风险等级、需人工判断的点、可能的错误、评审问题、是否需要领域签字。

合格例 1：
> 风险：中。需人工看：3 条结论的规范适用是否过时；2 处“需外部律师确认”的边界是否合理。评审问题：如果把第 39 条换成第 40 条，结论是否改变？

合格例 2：
> 风险：高（涉及健康信息）。需人工看：所有侧车字段是否残留身份信息；BIDS 转换是否改变方向/单位。评审问题：validator 通过但字段错误的情况如何发现？

不合格例 1：
> 无风险。

不合格例 2：
> 请评审看着办。

常见错误：所有任务都写“低风险”；不写具体检查点；把评审问题写成“是否优秀”。

## 13. provenance：来源、日期、许可、脱敏

**必须写**：每个资料的来源、获取日期、作者/机构、许可、是否修改、脱敏方法、可追溯 ID。

合格例 1：
> M1 来自XX市人社局 2024-03-01 发布的示范文本，政府公开，未修改；M2 为项目合成，作者张三，CC0；M3 来自官方法规库，版本 2024-01-01。

合格例 2：
> M1 为 OpenNeuro `ds000001` 子集，CC0，下载于 2026-11-01，仅保留 3 名受试者；已用 `pydeface` 去脸；原始 DICOM 不进入任务包。

不合格例 1：
> 资料来自公开网络。

不合格例 2：
> 数据已脱敏（没说方法、没说什么被删）。

常见错误：许可写“免费”；日期缺失；脱敏只说“处理过”；把受控数据写成公开。

## 14. handoff：让工程侧能接住

**必须写**：交付包清单、文件大小、运行命令、已知限制、未决项、联系人、版本号。

合格例 1：
> 包内：`task_source.json`、`materials/`（3 文件，12 MB）、`output/`（4 文件）、`run.md`。已知限制：法条库为 2024 版，2025 修订未覆盖。未决：第 3 条结论需外部律师确认。

合格例 2：
> 包内：`task_source.json`、`bids/`（3 序列，180 MB）、`qc.csv`、`logs/`。已知限制：只验证了 3 名受试者，未做群体统计。未决：无。

不合格例 1：
> 都好了。

不合格例 2：
> 有问题再联系。

常见错误：没有版本号；不写运行命令；把“未决”藏起来；文件大小与实际不符。

## 15. 证据：每条成功标准都要有落点

**必须写**：证据类型、文件路径、生成方式、对应哪条成功标准、是否含敏感信息。证据不是“我觉得对”，是第三人能打开、能重算、能对照的东西。

三类证据：
1. 资料证据：来源 URL、获取日期、许可、SHA-256；证明“这份资料我有权用”。
2. 过程证据：命令、参数、版本、日志、中间表；证明“这个结果是怎么做出来的”。
3. 结果证据：交付物本身、校验输出、对比表、差异清单；证明“结果满足阈值”。

合格例 1：
> E1 `materials/M1.pdf`，SHA-256 `…`，来源 `https://example.gov/…`，获取 2026-11-01，政府公开；对应 M1。
> E2 `logs/pdftotext.log`，命令 `pdftotext -layout`，版本 24.02；对应 O1。
> E3 `output/citation_check.csv`，逐条列出法名、条号、生效日期、URL；对应 S1、S2。

合格例 2：
> E1 `bids/sub-01/` 的 `bids-validator` 完整输出 `logs/validator.txt`；对应 S1。
> E2 `logs/dcm2niix.log` 含版本、命令、3 个序列的转换结果；对应 O1。
> E3 `qc/defacing_check.png` 只含合成 Phantom，不含真实人脸；对应 S3。

不合格例 1：
> 证据：我检查过了，没问题。

不合格例 2：
> 证据：截图一张（含真实受试者面部）。

常见错误：证据与成功标准不对应；只给结论不给命令；日志被截断；证据文件路径在交付包里不存在；把受限数据截图当证据。

## 16. 资料与授权：四条硬规则

1. 公开：政府、法院、官方统计、开放期刊、CC0/CC-BY；保存 URL、获取日期、许可文本。
2. 合成：自己造，明确标“合成”，不用真实人名/机构名。
3. 脱敏：只用于必须的真实结构；删除直接标识符，处理准标识符，写清方法。
4. 禁止：患者影像、客户合同、在办案卷、业主能耗、未公开招标文件、付费数据库内容。

不确定时，默认不用。授权问题在评审阶段发现，整条任务退回，不计工时。

## 17. 常见退回原因

| 代码 | 退回原因 | 怎么改 |
|---|---|---|
| A1 | 工作流太浅，像问答 | 换成有输入、有步骤、有交付物的流程 |
| A2 | 资料不可授权 | 换公开/合成资料，或删掉该资料 |
| A3 | 步骤不可重做 | 补工具、版本、参数、判断点 |
| A4 | 交付物不清楚 | 补路径、格式、字段、命名 |
| A5 | 成功标准不可测 | 改成阈值/检查方法/证据位置 |
| A6 | 环境不可复现 | 写 OS、版本、离线要求、资源 |
| A7 | 身份信息未脱敏 | 删除/替换，写脱敏方法 |
| A8 | 引证不现行/不正确 | 逐条核对，标生效日期 |
| A9 | 单位/口径不一致 | 统一单位，写换算 |
| A10 | 与已有任务重复 | 换工作流变体或子域 |
| A11 | 十块缺项 | 按清单补齐 |
| A12 | 任务需要外部服务/Windows/GPU | 改题或标风险，试点不做 |

## 18. 一页提交前检查表

- [ ] 标题能检索，含专业动作与对象
- [ ] scenario 有角色、目标、期限、约束
- [ ] materials 每个文件有来源、许可、哈希、用途
- [ ] 无患者/客户/案卷/业主原始数据
- [ ] operations 5–12 步，有工具、版本、参数、失败分支
- [ ] 至少 2 个专业判断点
- [ ] deliverables 有路径、格式、字段、命名
- [ ] success_criteria 每条可检查，有阈值/证据
- [ ] environment 写清 OS、软件、离线、GUI/GPU
- [ ] review 写清风险与评审问题
- [ ] provenance 有日期、作者、许可、脱敏
- [ ] handoff 有包清单、运行命令、已知限制
- [ ] 十块无空项
- [ ] 预计工时与难度匹配
- [ ] 没有把工程侧命令写进专家步骤
- [ ] 自读一遍：陌生人能重做吗？

## 19. 一句话总结

合格任务 = 真实工作流 + 可打开的资料 + 可重做的步骤 + 可检查的交付物 + 可授权的来源。缺一项，就会被退回。
