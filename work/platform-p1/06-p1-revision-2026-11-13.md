# 平台 P1 修订设计，ALE-data 生产与入库

这份文件回答平台 P1 在 2026-11-13 新基线下的边界、状态机、数据模型、Agent 工作流、ALE-data 包契约、组包校验入库流程和功能验收。它取代 `01` 到 `05` 中与本文件冲突的部分；未冲突的容量、类目覆盖、设备与排期细节继续有效。

## 1. 修订原因

v1 把平台终点定在冻结快照与交接包，把 Harbor 转换写进平台需求，把试点成功定成四段全 PASS。这和 2026-11-13 的新基线冲突。新基线要求平台从规范任务源自动生成完整 ALE-data 包，完成校验与入库；Harbor 转换、运行、判分归工程，平台不碰。平台还要支撑三条试点从人工标注迁到平台辅助标注，并让 Agent 在五个环节提供可审计的建议。

## 2. 边界

平台做七件事。

1. 专家入驻、角色、权限、任务分配。
2. 规范任务源十块的编辑、校验、版本与提交。
3. 资料上传、哈希、许可、隐私、脱敏标记与四层资料隔离。
4. 自动检查、领域评审、质量审核、退回返修、冻结快照。
5. Agent 访谈、追问、结构化、预检、审核辅助，全部只写建议。
6. 从冻结快照自动生成 ALE-data 包，做 L1 到 L5 校验，失败隔离。
7. 包入库、版本、资产索引、审核记录、审计、库内取包与已入库修订。

平台不做六件事。

1. 不做 ALE 旧版运行格式转换，不做 Harbor 转换，不构建运行镜像。
2. 不启动任务容器或虚拟机，不跑验证器，不判分，不产生分数。
3. 不实现 Verifier 或 Judge 的工程逻辑。
4. 不做正式评测与排行榜。
5. 不让专家填 Dockerfile、验证器或任务目录。
6. 不把 Harbor 字段写进核心任务源 Schema。

平台与工程的唯一边界是 ALE-data 包。平台导出包和包清单，工程读包，按选定的运行框架转换、运行、判分；工程不连平台数据库。

## 3. 状态机

任务状态十一个，旁路 `returned` 与 `void`。

```
draft -> submitted -> auto_checked -> in_review -> approved -> frozen
      -> packaged -> package_validated -> ingested
```

- `submitted`、`auto_checked`、`in_review`、`approved` 可以回 `returned`，返修后再提交。
- `frozen` 之前可以 `void`；`frozen` 之后只能出新版本，不能作废。
- `packaged`、`package_validated`、`ingested` 是新增段。组包失败回 `frozen` 并记失败码；包校验阻断回 `frozen`；入库冲突进隔离区，不回退已发布版本。
- `handed_off` 删除。交接不再是状态，导出是 `ingested` 之后的一个动作。

入库记录有自己的状态：`received -> validating -> validated -> published`；`validating -> rejected`；`validated -> quarantined`；`published -> superseded / withdrawn`。任务状态与入库状态分开，避免把“包已生成”当成“已入库”。

## 4. 数据模型

保留 v1 的 `users`、`expert_profiles`、`categories`、`subdomains`、`tasks`、`task_versions`、`materials`、`checks`、`reviews`、`review_items`、`assignments`、`reviewers`、`snapshots`、`batches`、`audit_events`、`agent_suggestions`。做以下改动。

`tasks` 删除 `harbor_schema_version`，增加 `current_package_id`、`ingest_status`、`counted_in_500`。`counted_in_500` 只由合作方验收回执改写，平台不能自行置 true。

新增表：

| 表 | 关键字段 | 作用 |
| --- | --- | --- |
| `packages` | `package_id`、`task_id`、`task_version`、`package_version`、`ale_data_version`、`package_hash`、`native_hash`、`file_count`、`built_by`、`built_at`、`status`、`storage_path` | 一个冻结版本对应一个包；同版本重建必须同哈希 |
| `package_validations` | `validation_id`、`package_id`、`validator_version`、`l1` 到 `l5`、`blockers`、`warnings`、`report_path`、`created_at` | 每次校验留一行，不覆盖历史 |
| `ingest_records` | `ingest_id`、`package_id`、`task_id`、`package_hash`、`ingested_at`、`asset_index_count`、`status`、`counted_in_500`、`supersedes` | 入库回执；`package_hash` 与包必须一致 |
| `agent_runs` | `run_id`、`task_id`、`task_version`、`capability`、`model`、`model_version`、`prompt_hash`、`input_hash`、`output_json`、`cost_yuan`、`latency_ms`、`status` | 每次 Agent 调用可重放、可计费 |
| `pilot_feedback` | `pilot_id`、`task_id`、`segment`、`step`、`automation`、`manual_hours`、`platform_hours`、`issue`、`expert_id` | 三条试点的分段耗时与卡点 |
| `feature_flags` | `flag`、`scope`、`enabled`、`version`、`changed_by`、`changed_at` | 试点只开已验收的开关 |
| `library_exports` | `export_id`、`package_id`、`target`、`requested_by`、`created_at`、`status` | 库内取包与对外导出 |

`materials` 增加 `role`，取 `raw`、`deidentified`、`work`、`reference`。原始资料永不被脱敏副本覆盖。

`agent_suggestions` 增加 `run_id`、`field_path`、`value_json`、`confidence`、`status` 取 `pending`、`accepted`、`edited`、`rejected`，以及 `confirmed_by`、`confirmed_at`。没有确认行的建议不得写入任务源。

## 5. Agent 工作流

Agent 做五件事，每件单独开关、单独计费、单独评估。

| 能力 | 输入 | 输出 | 人工确认点 |
| --- | --- | --- | --- |
| 访谈 | 任务方向、专家画像、已有草稿 | 结构化问题清单 | 专家逐条回答或跳过 |
| 追问 | 任务源缺口、前后矛盾 | 追问与建议补全 | 专家接受、修改或拒绝 |
| 结构化 | 自由文本、资料清单 | 十块字段草稿 | 专家逐字段确认 |
| 预检 | 任务源、包草稿 | 缺件、歧义、许可、泄漏、可验证性提示 | 专家与评审确认 |
| 审核辅助 | 任务源、评审规则 | 阻断候选、非阻断建议、引用位置 | 评审人决定 |

硬规则：

- Agent 只写 `agent_suggestions` 与 `agent_runs`，不直接改 `task_versions`、`materials`、`reviews`、`packages`。
- 建议必须有 `model`、`model_version`、`prompt_hash`、`input_hash`、`confidence`。没有来源的建议按失败处理。
- 专家确认后才能写入；自动采纳按失败处理。`edited` 要保留原值与改后值。
- Agent 不能改许可、PII、IRB 状态，不能提交、冻结、组包、校验、入库，不能改包。
- 单任务 Agent 成本上限 120 元，试点 60 元；p95 首 token 不超过 8 秒，结构化不超过 60 秒，预检不超过 90 秒。超限降级为模板加人工，不静默重试。
- Agent 质量报告按五项能力记录样本量、成功率、人工修改率、阻断漏报、单条成本；阻断级漏报必须为 0。

## 6. ALE-data 包契约

### 6.1 布局

```
packages/<domain_code>/<task_slug>/<task_version>/
  base/
    PACKAGE.json
    input/
      <task brief 与资料，文件名保持原样>
      document_manifest.json     # 有 documents/ 时
      documents/
      runtime_env/
    software/
    reference/
      answer_key.json            # 有 oracle 时
  SHA256SUMS
  package_manifest.json
  validation_report.json
  materials.json
  provenance.json
  handoff.json
  supersedes.json                # 仅修订版
```

`base/` 与官方 `ale-data` 原生布局一致。`PACKAGE.json` 允许放在 `base/`，但计算 `native_hash` 时排除它，避免边车改动被当成内容改动。版本级边车不参与 `native_hash`，参与 `package_hash`。

### 6.2 PACKAGE.json 字段

必填：`schema_version` 固定 `ale-pkg-1.2`；`ale_data_version` 固定 `task-data-v1.1`；`task_id`；`task_version`；`domain_code`；`subdomain_code`；`title`；`summary`；`language`；`entrypoints`；`deliverables`；`oracle`；`environment_intent`；`sandbox`；`license`；`provenance`；`pii`；`files`。

`entrypoints` 用角色声明路径，不强制改文件名：

```json
{
  "brief": "input/task_brief.md",
  "contract": "input/output_contract.json",
  "answer_key": "reference/answer_key.json",
  "document_manifest": "input/document_manifest.json"
}
```

只有 `brief` 与 `contract` 必填；`answer_key` 在 `oracle.required=true` 时必填；`document_manifest` 在有 `documents/` 时必填。角色路径必须是包内相对路径，不得绝对路径，不得 `..`。

`contract.kind` 取五种：`numeric_cases`、`tabular_columns`、`document_qa`、`artifact_diff`、`code_artifact`。未知 kind 进隔离区，不静默当通用契约。

`license` 三态：`cleared`、`pending`、`restricted`。`pending` 与 `restricted` 不得入库为可计数包；`restricted` 可以进库但 `counted_in_500=false`，并标 `scope_exception`。

`files[]` 每项含 `path`、`sha256`、`bytes`、`mode`、`role`。`role` 取 `input`、`software`、`reference`、`document`。`software` 保留可执行位。`native_hash` 是 `base/` 内容按路径排序后的规范哈希，排除 `PACKAGE.json`。

`sandbox.input_root` 与 `sandbox.output_root` 用包内相对角色，不得写宿主机绝对路径。`environment_intent` 只写意图，不写 Dockerfile。

`review`、`sign_offs`、`batch_id`、`owner_expert_id` 不进包；这些留在平台库与审核记录。`provenance` 与 `license` 必须进包，保证包离开平台仍可追溯。

### 6.3 包哈希

`package_hash` 覆盖 `base/` 全部文件、`PACKAGE.json`、版本级 `package_manifest.json`、`materials.json`、`provenance.json`、`handoff.json`。`validation_report.json` 不进 `package_hash`，否则校验会改变哈希。`SHA256SUMS` 覆盖 `base/` 与版本级边车，排除自身。

同一冻结快照重建，`native_hash` 与 `package_hash` 都必须一致；时间戳、导出人、报告路径不得进哈希。

## 7. 组包、校验、入库

### 7.1 组包

组包唯一输入是 `frozen` 快照。流程：

1. 读冻结快照与任务源十块，拒绝任何非冻结版本。
2. 按 `entrypoints` 复制 `input/`、`software/`、`reference/`，不改文件名，中文 NFC 归一化。
3. 生成 `PACKAGE.json`，填 `built_by=platform`、`task_version`、`ale_data_version`、`files[]`。
4. 生成 `package_manifest.json`、`materials.json`、`provenance.json`、`handoff.json`，计算 `native_hash` 与 `package_hash`。
5. 写临时目录，校验通过后原子移动到 `packages/`；失败留临时目录与失败码，不产生半包。
6. 同一 `task_id + task_version` 已存在且哈希相同，直接返回已有包；哈希不同拒绝并告警，不覆盖。

组包必须幂等。重跑不改变哈希，不产生重复包，不重复扣 Agent 成本。

### 7.2 校验 L1 到 L5

| 层 | 检查 | 阻断示例 |
| --- | --- | --- |
| L1 结构 | 目录、`PACKAGE.json` 可解析、路径安全、角色路径存在 | `PKG_LAYOUT`、`PKG_PATH_UNSAFE`、`PKG_ENTRYPOINT_MISSING` |
| L2 语义 | 域与子域存在、slug、task_id 前缀、版本、contract.kind | `PKG_DOMAIN_UNKNOWN`、`PKG_VERSION_UNSUPPORTED`、`PKG_CONTRACT_KIND` |
| L3 完整性 | `files[]` 覆盖全部文件、哈希复算、manifest 与 documents 一致 | `PKG_HASH_MISMATCH`、`PKG_FILE_UNLISTED` |
| L4 安全授权 | 许可状态、PII、来源、绝对路径、答案泄漏 | `PKG_LICENSE_MISSING`、`PKG_PII_HIGH`、`PKG_ANSWER_LEAK` |
| L5 入库一致性 | 同任务同版本冲突、`supersedes` 存在、`counted_in_500` 条件 | `PKG_VERSION_CONFLICT`、`PKG_SUPERSEDES_MISSING` |

一次返回全部发现，每条含 `code`、`path`、`message`、`severity`。阻断任一即拒绝；警告不阻断但必须进报告。单包大于 5 GiB 阻断，大于 1 GiB 警告；确有 12 GiB 级资产时由负责人批准 `external_ref`，不把大文件塞进 git。

官方 122 条只作回归样本：它们没有 `PACKAGE.json`，导入前由工程补边车；不计 500，不占编号，不进正式库。

### 7.3 入库

入库按 `package_hash` 幂等。流程：

1. 写 `ingest_records`，状态 `received`。
2. 复核包哈希与 `package_validations` 最新报告；不一致进 `rejected`。
3. 校验 L5 与任务版本冲突；同任务已有 `published` 版本时，新包必须带 `supersedes`。
4. 写任务、版本、资产索引、审核引用，状态 `published`。
5. 修订先建新包与新版本，成功后再把旧版本标 `superseded`；不做原地覆盖。
6. 失败进隔离区，保留原包与报告；不产生部分入库，不改已发布版本。

`counted_in_500` 默认 false。只有合作方验收回执到达后，由负责人或合作方接口人改写；平台不能因为 `published` 就置 true。

## 8. 功能验收

### 8.1 M1a，分两段，支撑首批 30 开工

M1a-Core，2026-11-30，六项：账号与六角色权限；任务源编辑器与 Schema 校验；资料上传、哈希、许可、PII 字段；评审队列、派单、退回返修；冻结快照；审计日志。

### 8.2 M1b，2026-12-22，支撑首批 30 组包入库

四项：ALE-data 组包器；L1 到 L5 校验器；幂等入库与冲突隔离；法律供应方导入校验的正反样本。

法律 8 条 12-08 到包，12-12 前用工程脚本或 S2 手工预检完成布局、契约、哈希三项并留报告；12-15 后用 S3 校验器复跑 L1 到 L3；12-22 到 12-23 走 M1b 的 L4 到 L5 正式校验与幂等入库。预检不等于 M1b 验收，入库必须等 M1b 验收通过。

### 8.3 M2，分两段，支撑 W1 余 90 与四批

M2-C，2026-12-31 前，W1 余 90 开工必需的子集：自动派单优化、评审质量看板、对象存储分层。M2-C 必须在 90 条 01-01 开工前通过。

M2-Full，2027-01-31 前：自动脱敏、富报表、多语言、单点登录、Agent 深度集成。M2-Full 不阻塞 90 条开工，但必须在 W2 扩量前完成。
