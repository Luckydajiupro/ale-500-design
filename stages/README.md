# 阶段索引

这份文件回答一件事：项目有哪几个阶段，每个阶段的产出放在哪，现在做到哪。读完这一份就知道该进哪个目录。

每个阶段一个目录，进去先读 `STAGE.md`。冻结的产出不在这里改写，要补充说明写在 `STAGE.md`。

|---|---|---|---|

| 1 类别与专家研究 | `stages/s1-research/` | 已收口，已签字 | 52 份研究文件、40 个脚本、校验基线 |

已关闭和已收口的两个阶段，整个目录随仓库分发。克隆下来就能跑它们各自的校验命令，所以表里「产出」一列的数量是可核对的，不是描述性的。尚未建立的四个阶段没有目录，也没有检查命令。

## 什么内容进阶段目录

判据只有一条。这份内容的用途是证明某一刻是什么，还是告诉人接下来怎么做。

证明某一刻是什么的，进 `stages/sN-<短名>/`。校验和、运行记录、逐条判定、验收回执、某一批次的质检卡片。

告诉人接下来怎么做的，只进 `docs/`。字段映射、交接合同、参数阈值、流程规定。

同一条内容不会同时出现在两边。设计文档描述格式，每条任务的快照按这个格式生成并被哈希，两者不是同一份东西。

阶段 5 量产时要特别当心。500 条任务本身不进 git，进阶段目录的是批次质量卡片、例外清单，以及交付包的位置和哈希。

## 阶段目录里有什么

`STAGE.md` 是入口，写清这个阶段做了什么、结论是什么、怎么复验、有哪些限制。

同一目录下的其他文件是当时的原始产出，保持原样。它们可能互相引用，也可能写着当时的旧路径，这些都不改，因为校验和绑定的是当时那一版字节。

## 阶段目录里没有什么

没有正在使用的设计。设计只放在 `docs/`。阶段目录是历史快照，不是工作区。
