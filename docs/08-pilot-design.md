# 三条试点详细设计

这份文件回答三条试点怎么从专家人工标注迁到平台辅助标注、平台和 Agent 怎么同步调试、试点怎么判定通过。它把 `docs/02-plan.md` 阶段 2 的出口展开成可执行的周计划、记录格式和验收判据。

试点不计入 500。试点是能力探索，不是缩小的批量生产；首批 30 条才是正式生产第一梯队。

## 试点要回答的三个问题

第一，专家人工做一条任务，时间花在哪、资料卡在哪、哪些判断说不清。没有这份基线，平台表单和 Agent 追问就没有依据。

第二，平台把人工步骤接过去之后，专家是不是更快、返工是不是更少、质量是不是不掉。平台不是把纸表搬到网页，而是改字段、改流程、改校验。

第三，Agent 在访谈、追问、结构化、预检、审核辅助五件事上，哪些已经可用、哪些只会添乱、单条成本多少。Agent 只出建议，专家逐字段确认，不允许自动采纳。

三个问题对应三条同步工作线。A 线专家人工标注，B 线平台开发与试用，C 线 Agent 配置与调试。三条线在 2026-11-18 到 12-30 之间并行，不是先后做完再交接。

## 三条试点和任务边界

| 方向 | domain_code | 试点任务示例 | 为什么选它 |
|---|---|---|---|
| 商业 | business_finance | `business_finance/accounting_reconcile_01` | 资料以表格和凭证为主，结构清楚，适合看人工到平台的迁移 |
| 神经影像 | psychology_neuro | `psychology_neuro/dicom_to_bids_01` | 有专业工具和文件格式，能暴露平台表达不了的隐性步骤 |
| 建筑节能 | engineering | `engineering/building_energy_baseline_01` | 有计算和外部规范，能测 Agent 追问和预检的边界 |

三条试点各 1 条，不要求覆盖全部 14 个域，也不承担配额验证。每条试点只做基线复算与可验证性检查，不出具执业结论；建筑试点不要求外部注册工程师签字，500 条里的建筑任务仍按 `docs/04-roles-and-decisions.md` 第十四条签字后放行。

试点任务用公开数据或合成资料，不接触真实客户材料。资料授权按 `docs/06-decisions-and-blockers.md` 的默认走法执行；需要新授权时，先停该条试点，不先用后补。

## 三条工作线

三条线各自有负责人、交付物和周节奏，但在同一张周表上对齐。任何一条线停摆，另外两条线照常推进，停摆的段在问题清单里标出来。

### A 线，专家人工标注

专家在平台外用固定模板做一条任务，记录七段的开始时间、结束时间、耗时、资料清单、卡点、判断依据和返工。模板不追求好看，追求能对比。每一段至少记四个字段：输入、动作、输出、耗时。

人工基线不是让专家随便做一遍。任务范围、交付物、成功标准在 11-21 前冻结，三条试点用同一版模板和同一版标注规范。专家可以查资料、用工具、问人，但要把这些动作记下来，因为它们正是平台要接过去的部分。

### B 线，平台开发与试用

平台按周交付可用版本，不等到功能齐了再给专家。每个版本只改一小块，专家当周试用，周末给反馈，下一周改。

| 时间 | 平台版本 | 这一版必须能用 | 专家怎么用 |
|---|---|---|---|
| 11-30 | S0 | 账号、任务源表单 v0、资料上传、哈希、审计 | 把人工基线的一条任务录入，找字段缺失 |
| 12-04 | S1 | 评审队列、派单、退回返修、冻结快照 | 走一次提交和退回，记录返修轮次 |
| 12-08 | S2 | Agent 建议面板、逐字段确认、表单 v1 | 用 Agent 起草，专家逐字段改 |
| 12-15 | S3 | 组包器 beta、包校验 L1 到 L3、失败隔离 | 用冻结快照生成一个包，看缺件和哈希 |
| 12-22 | S4 | 包校验 L4 到 L5、幂等入库、入库回执 | 完成组包、校验、入库全链 |

平台版本用功能开关控制，试点专家只看到已验收的开关。S3 和 S4 的包格式按 `docs/08-pilot-design.md` 附的 ALE-data 契约草案执行；契约变化要同时改组包器、校验器和试点记录，不能只改一边。

平台侧要埋点，不靠事后访谈回忆。每个字段的填写耗时、Agent 建议的展示与采纳、退回原因、组包失败码、入库耗时，都要有记录。埋点字段在 11-21 前定版，之后只增不改。

### C 线，Agent 配置与调试

Agent 做五件事，每件事单独开关、单独记录、单独评估。

1. 访谈。按任务方向问背景、目标、输入、约束、交付物、成功标准，把专家口头经验转成问题清单。
2. 追问。发现字段空、前后矛盾、资料缺失、成功标准不可观测时，追问到能落字段为止。
3. 结构化。把访谈和资料整理成规范任务源十块草稿，字段级给出处。
4. 预检。检查契约一致、资料引用、环境依赖、交付物路径、成功标准可观测性，给出阻断和建议两级。
5. 审核辅助。给评审人列出检查项、证据位置、可能争议点，不替评审人下结论。

Agent 的输出一律是建议。专家逐字段选择接受、修改或拒绝，记录确认人和确认时间。没有确认的建议不写入任务源。Agent 不能改许可、PII、IRB 状态，不能提交、冻结、组包、校验、入库，不能改包。

Agent 的效果指标在试点前定好，试点中只记录不改口径。

| 指标 | 怎么量 | 试点门槛 |
|---|---|---|
| 建议采纳率 | 被专家接受或修改后保留的字段数除以建议字段数 | 五项都有数据；至少两项达到 40% |
| 净节省时间 | 人工基线耗时减平台辅助耗时，再减专家确认耗时 | 至少两项为正 |
| 误报率 | Agent 标阻断但专家判定不阻断的比例 | 每项都记录，不设统一门槛 |
| 漏报 | 评审或工程发现但 Agent 没标的问题数 | 每项都记录，阻断级漏报为 0 |
| 单条成本 | 模型调用、重试、人工确认折算 | 试点不超过 60 元一条 |
| 延迟 | 首 token、结构化完成、预检完成 | p95 分别不超过 8 秒、60 秒、90 秒 |

试点不要求五项全达标。要求五项都有样本、都有失败模式、都有成本数；至少两项对专家有净节省；阻断级漏报为 0；自动采纳为 0。达不到的项写进 Agent 能力报告，作为 M2 的 backlog，不硬推。

## 七段链和周计划

每条试点走七段：人工标注基线、平台辅助标注、专家确认、独立审核、ALE-data 组包、包校验、入库。

| 周 | 日期 | A 线 | B 线 | C 线 | 产出 |
|---|---|---|---|---|---|
| 1 | 11-13 到 11-17 | 触达 3 名专家，确认方向 | 账号、存储、审计骨架 | 选模型与提示词基线 | 3 份意向确认 |
| 2 | 11-18 到 11-21 | 签约、培训、任务范围冻结 | S0 表单 v0 | 访谈提纲 v0 | 合同、协议、任务范围 |
| 3 | 11-24 到 11-28 | T1 人工基线，三条各 1 条 | S0 试用，收字段缺口 | 访谈与追问试跑 | T1 记录、字段缺口清单 |
| 4 | 12-01 到 12-05 | T1 收尾，补资料与判断 | S1 评审与冻结 | 结构化草稿对比 | T1 完成、S1 验收 |
| 5 | 12-08 到 12-12 | T2 平台辅助，三条各 1 条 | S2 Agent 面板、表单 v1 | 五项能力全开 | T2 记录、建议日志 |
| 6 | 12-15 到 12-19 | T2 收尾，专家逐字段确认 | S3 组包 beta | 预检与审核辅助 | 确认记录、S3 验收 |
| 7 | 12-22 到 12-25 | 配合组包与返修 | S4 校验与入库 | 失败模式复盘 | 3 个包、校验报告、入库回执 |
| 8 | 12-28 到 12-30 | 问题清单收口 | 试点验收 | 能力报告定稿 | 试点 gate |

T1 和 T2 用同一题族的不同实例，中间至少隔 3 个工作日。专家在 T1 之后不接触 T2 实例，避免把 T1 的答案带过去。T2 的 Agent 建议不能引用 T1 的产出，除非该产出已经进入共享资料库并在记录里标明。

可选的 T3 影子件用于分离“平台效应”和“练习效应”。T3 由同一专家在 T2 之后再做一条同题族新实例，只用平台、不开 Agent；如果时间不够，T3 可以不做，但要在报告里说明缺 T3 对结论的限制。

## 记录格式

每条试点一个 JSON 记录，三条记录放在同一目录，目录里另有索引和证据文件。字段名用英文，值可以用中文。记录只写事实，不写评价；评价放问题清单和能力报告。

单条记录至少包含：

- `task_id`、`direction`、`expert`、`signed_at`。
- `manual_baseline`：起止时间、小时数、资料清单、卡点、标注规范版本。
- `platform_assisted`：起止时间、小时数、表单版本、Agent 调用次数、建议数、采纳数、专家确认、确认时间、人工兜底清单。
- `review`：评审人、是否独立、轮次、阻断数、解决数、批准时间。
- `package`：路径、包哈希、文件数、ALE-data 版本、是否平台生成、重建哈希、是否一致。
- `validation`：校验器名称与版本、检查项、通过数、阻断数、警告数、报告路径。
- `ingest`：入库记录 ID、入库时间、包哈希、资产索引数。

索引另记三项共用证据：自动化/人工分工矩阵、可复用标注规范、Agent 能力报告；另加问题清单和工程冒烟记录。记录格式的机器校验由 `tools/exit/pilot_gate.py` 执行，人工只填不改结构。

索引文件固定叫 `index.json`，三条记录固定叫 `record-*.json`，一共三个。索引字段如下。

- `schema_version` 固定 `pilot-index-1.0`，`pilot_id` 非空，`task_ids` 恰好三个且不重复。
- `artifacts.division_matrix`：`path`、`version`、`steps` 固定 7、`assisted` 至少 1、`manual` 至少 1、`manual_hours` 与 `platform_hours` 均为正数。
- `artifacts.annotation_spec`：`path`、`version`。
- `artifacts.agent_report`：`path`、`version`、`capabilities` 固定 5、`details` 恰好 5 项；每项有 `capability`（`interview`、`follow_up`、`structuring`、`precheck`、`review_assist` 之一）、`sample_size` 正整数、`success_rate` 在 0 到 1、`cost_per_task` 非负、`failure_modes` 非空列表。
- `artifacts.smoke`：`path`、`version`、`status` 取 `PASS`、`SKIP`、`FAIL`；`FAIL` 直接不通过，`SKIP` 必须有 `reason`。
- `artifacts.issue_log`：`path`、`version`、`open_blockers` 固定 0、`fallbacks` 是人工兜底 ID 列表。

单条记录的七段字段必须齐全。`manual_baseline` 的 `hours` 大于 0，`artifacts` 非空；`platform_assisted` 的 `agent_suggestions` 大于 0，`agent_accepted` 不超过建议数，`expert_confirmed` 为 true；`review.reviewers` 不含专家本人，`blockers` 等于 `resolved`；`package.package_hash` 是 64 位小写十六进制，`rebuilt_hash` 与它相等；`validation.passed` 等于 `checks`，`blockers` 为 0；`ingest.package_hash` 等于包哈希，`ingested_at` 不早于 `review.approved_at`。

检查器自检覆盖二十四组人造记录，包括缺段、未确认、包哈希错、校验阻断、入库错配、重复方向、分工矩阵缺步或缺工时、Agent 报告缺项、冒烟 FAIL 或 SKIP 无理由、坏 JSON。自检本身不通过，检查器的通过不算证据。

## 十二项证据

| 证据 | 必须包含 | 缺失即失败 |
|---|---|---|
| E1 人工基线 | 每条起止、小时、资料、卡点、专家判断 | 任一条没有，失败 |
| E2 平台辅助 | 表单版本、Agent 调用、建议数、采纳数、确认时间 | 任一条没有，失败 |
| E3 专家确认 | 逐字段确认标记，未确认建议不得入包 | 任一条未确认，失败 |
| E4 独立审核 | 评审人不是作者，轮次、阻断、解决、批准时间 | 只有自评，失败 |
| E5 ALE-data 包 | 路径、包哈希、文件数、`task-data-v1.1` | 缺包或版本不对，失败 |
| E6 包校验 | 校验器名称与版本、检查项、阻断数、警告数 | 有阻断，失败 |
| E7 入库记录 | 记录 ID、时间、包哈希、资产索引数 | 哈希对不上，失败 |
| E8 分工矩阵 | 七步各自的 auto/assisted/manual、人工小时、平台小时 | 缺矩阵或漏步，失败 |
| E9 标注规范 | 版本、字段定义、示例、验收 rubric，三条共用 | 缺规范，失败 |
| E10 Agent 报告 | 五项能力的样本、成功率、失败模式、单条成本 | 缺报告，失败 |
| E11 问题清单 | 未关闭阻断为 0，人工兜底逐条申报 | 有未申报兜底，失败 |
| E12 工程冒烟 | 包可解析、字段可映射、少量格式可转换；允许 SKIP 写理由 | 冒烟 FAIL 不直接判失败，但不能替代出口 |

证据不是附件堆。每条证据要能追到任务、版本、时间和责任人；包哈希、入库哈希、重建哈希三处必须能互相对上。

## 试点通过判据

试点通过要同时满足十二条。

1. 三条试点七段全链走完，方向是商业、神经、建筑，没有重复。
2. 三条都有人工基线、平台辅助、专家确认、独立审核、包、校验、入库。
3. 3 个包由平台生成，`built_by=platform`，不是手工拼装。
4. 包哈希可从同一冻结源重建，重建哈希与包哈希一致。
5. 包校验零阻断，警告逐条有解释。
6. 入库记录与包哈希一致，入库时间不早于审核批准。
7. 专家逐字段确认，Agent 建议自动采纳为 0。
8. 人工兜底逐条申报，分工矩阵覆盖七步，至少一个 assisted、一个 manual。
9. 标注规范 v1 三条共用，版本与记录一致。
10. Agent 报告覆盖五项能力，每项有样本、成功率、失败模式、单条成本。
11. 问题清单未关闭阻断为 0。
12. 工程冒烟记录存在；允许 SKIP，但 PASS 不能替代以上十一条。

任一条不满足，阶段 2 不通过。不能把“三条都做完了”当成通过；做完不等于证据齐全。

## 试点失败和回退

失败分三种。第一种是能力不成立，平台或 Agent 在关键步骤上帮不上忙，专家反而更慢。第二种是证据不成立，包重建不了、哈希对不上、审核不独立。第三种是范围失控，资料授权、执业签字、外部服务把试点拖成工程项目。

第一种失败的处理是缩范围，不硬推。把 Agent 从五项缩到两项，把平台从全链缩到表单加冻结，把试点从三条缩到两条；缩范围要负责人批准，并在问题清单里写清缩了哪一段、对阶段 2 出口有什么影响。

第二种失败的处理是回退到上一个稳定版本，修包和校验器，不修记录。记录不能为了通过而改；包可以重建，记录不行。

第三种失败的处理是换任务，不换标准。建筑执业签字、客户资料授权、外部服务联网，任一项在 11-25 前没有答案，就换同方向的公开资料任务，保持三条试点方向不变。

## 和首批 30 条的关系

试点不是首批 30 条的硬前置。首批 30 条在 M1a 通过后于 12-01 开工，用平台 S0/S1 做任务源、审核和冻结；组包和入库等 M1b 在 12-22 通过后做。试点每周的结论进 30 条的周会，不改 30 条的开工日。

首批 30 条的法律 8 条不经过试点。法律走供应方 ALE-data 导入，12-08 到包，12-12 前导入校验，12-15 前入库；不通过则 30 条变 22 条，报实际数，不用别的任务顶替。

试点不产生可对外的专家人数。3 名试点专家是否进 W1，由专家运营负责人在 12-15 前按产能和意愿决定；进 W1 要重新签批次合同，不能沿用试点合同。

## 角色和分工

项目负责人定试点范围、出口判据、缩范围和换任务。专家运营负责人管签约、培训、排期和专家沟通。领域负责人管任务范围、标注规范、专业争议。平台产品与工程管 S0 到 S4、埋点、功能开关。Agent 负责人管提示词、工具白名单、成本、日志。质量负责人管独立审核、证据完整性。工程负责人管冒烟和包可转换性。隐私安全负责人管资料授权、脱敏、PII。合作方接口人不参与试点执行，只在阶段 2 收口时看证据。

试点专家只对专业内容和确认负责，不碰 Docker、验证器、任务目录和包结构。平台和 Agent 不替专家做专业判断，工程不替专家改业务内容。

## 风险和对策

| 风险 | 早期信号 | 对策 |
|---|---|---|
| 专家把平台当纸表，迁移没有发生 | 平台段耗时不低于人工段，返工轮次不降 | 先改字段和校验，不加页面；每周只看三个卡点 |
| Agent 建议太多，专家确认更慢 | 建议采纳率低于 20%，确认时间超过节省时间 | 缩到两项能力，按字段给建议，不做整篇生成 |
| 包格式反复变，组包器追不上 | 同一周两次契约变更 | 契约冻结到 12-15，之后只加不改；变更走版本号 |
| 资料授权拖住试点 | 11-25 仍没有书面许可 | 换公开资料任务，不碰客户材料 |
| 审核不独立，证据自证 | 评审人等于专家，或评审只有一轮 | 评审人从专家池另派，记录评审人 ID 和轮次 |
| 试点被当成 30 条的前置 | 30 条等试点 gate 才开工 | 30 条按 M1a 开工，试点结论只做输入 |
| 工程冒烟被当成出口 | 用冒烟 PASS 宣布阶段 2 通过 | 冒烟单独记录，阶段 2 只看十二项证据 |

## 负责人要拍板的事

试点双跑补贴。3 条试点要做人工基线和平台辅助两段，专家实际工时高于原试点包干。建议单列补贴，不挤占 500 条任务费；金额由负责人定。

建筑试点的签字范围。建议只做基线复算与可验证性检查，不出节能结论，不要求执业签字；如果负责人要求签字，试点时间要加两周，并可能换任务。

试点资料授权。建议只用公开数据与合成资料；如果要用客户材料，先走隐私安全审查，时间另算。

Agent 单条成本上限。建议试点 60 元、正式 120 元；超过上限时缩能力，不缩确认。

3 名试点专家是否进 W1。建议由专家运营负责人按产能决定，不默认全进；进 W1 要重新签批次合同。

## 阶段 2 收口后交什么

交给阶段 3 和阶段 4 的是六样东西：三条试点记录、十二项证据、标注规范 v1、Agent 能力报告、问题清单、阶段 2 验收结论。平台组包器、校验器、入库接口的代码和测试留在平台分支，阶段 3 继续用。

阶段 2 收口不等于平台 M1 完成。M1a 在 11-30 验收，M1b 在 12-22 验收，M2 在 2027-01-31 前验收；阶段 2 只用 M1a 和 M1b 的试点段，不替阶段 3 验收全部能力。
