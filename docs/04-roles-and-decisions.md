# 角色与决策状态

这份文件回答两件事：谁有权决定什么，以及哪些事已经决定、哪些还没决定。读完这一份就知道遇到一个争议该找谁，也知道现在有多少事悬着。

## 七个执行角色

| 角色 | 负责什么 | 不负责什么 |
|---|---|---|
| 专家 | 专业内容、原始资料、预期产物、成功标准、自检 | Docker、验证器、任务目录、环境依赖 |
| 领域评审人 | 专业真实性、术语、工作流、结果判断、重复裁定 | 格式转换、环境搭建 |
| 质量审核人 | 结构完整性、可复现性、证据、风险分级 | 专业结论本身 |
| Agent | 访谈、结构化、预检、问题解释、风险提示 | 专业正确性、授权合法性、最终放行 |
| 平台 | 字段、权限、状态、文件、审计、交接快照 | 内容判断、运行评测 |
| 工程人员 | 格式、环境、验证器、运行、评测、交付 | 修改专家业务内容 |
| 项目负责人 | 范围、决策、资源、门禁、例外、批次放行 | 替代领域专家做专业判断 |

## 七个管理职责

项目负责人管目标、范围、资源、阶段门禁、重大决策和最终交付。专家运营负责人管招募、培训、排班、产能、合作和沟通。领域负责人管任务族、专家画像、专业校准和争议仲裁。隐私安全负责人管原始资料、脱敏、权限、保密和合规。平台产品与工程管字段、状态、审核、Agent、存储、审计和导出。工程负责人管转换、环境、验证器、运行、评测和交付。合作方接口人管交付合同、验收标准、抽验和反馈。

## 决策分四层

项目负责人定目标、范围、配额、预算、时间和批次放行。

领域专家定专业边界、工作流、成功标准，以及两条候选算不算重复。

工程负责人定格式、环境、验证器、运行方式和技术可行性。

合作方定最终交付格式、验收规则和版本要求。

任何角色不能越权替其他角色作决定。工程不能因为"跑不起来"就删掉任务的复杂度，专家不能因为"我觉得对"就绕过验证器，平台不能替专家判断专业正确性。

## 什么情况要改设计，什么情况不改

改设计的情况：项目目标或计数口径变化、平台范围变化、阶段顺序或依赖变化、规范任务源或交接合同变化、质量闸门或责任边界变化、合作方交付格式或验收规则变化。

不改设计的情况：普通进度、临时问题、单条任务修订、验证日志、某条任务返修。这些记在阶段目录里，不上升到总体设计。

改设计时要写清四件事：这次吸收了哪些阶段成果、哪些设计变了、哪些问题仍然开放、对后续阶段有什么影响。
