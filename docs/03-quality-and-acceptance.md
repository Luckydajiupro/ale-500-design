# 质量与验收

这份文件回答一件事：一条任务做到什么程度才算合格，一条任务不合格时卡在哪一层。读完这一份能独立判断一条任务该不该放行。

## 质量分五层

五层是叠加的，下面一层不过，上面一层不用看。

第一层，内容真实性。任务来自真实业务，专业上站得住，有真实的工作价值。判断依据是专家背景、业务场景和资料出处，不是文字是否通顺。

第二层，任务契约一致。目标、输入、约束、预期产物、成功条件这五样互相对得上。常见失败是说明里要求 A，输入资料只支持 B，验证器却按 C 判分。

第三层，工程可执行。环境能构建，依赖能装，资产能取到，任务能启动并跑完。这一层不过，后面全都是空谈。

第四层，评价有效。验证器或评分方法真的在测任务目标，而不是在测有没有留下某个文件、有没有打印某行日志。这一层最容易出假阳性。

第五层，交付可复现。版本、哈希、日志、清单、运行条件完整，别人拿到能重现同样的结果。

## 每个任务都要过的自动检查

所有任务无条件执行下面九项，不看风险等级。

Schema 和字段完整性检查。文本和字段之间的一致性检查。资产存在性、引用关系和哈希检查。脱敏状态和敏感信息扫描。重复和高度相似检测。环境和软件依赖检查。Engineering Ready 生成检查。目标格式预检。lint、prepare、validate 和必要的冒烟运行。

自动检查只负责筛掉明确不合格的，不负责证明合格。通过自动检查的任务不等于可以交付。

## 风险分三层，审核强度不同

| 风险层 | 典型特征 | 审核策略 |
|---|---|---|
| 低 | 环境简单、资料明确、验证规则清楚、专家已认证 | 自动检查为主，抽样人工复核 |
| 中 | 步骤复杂、需要专业判断、多种输入或外部软件 | 独立同行评审，一名不是作者的领域评审人，由系统从专家池自动派单 |
| 高 | Windows 或 GUI、敏感资料、外部服务、复杂评分器、低置信度、多条阻断提示 | 全量人工审核，必要时加安全和工程复核 |

分层参数目前没有冻结。抽样率、风险阈值、审核人数都是建议值，要等首批 30 条跑完由项目负责人定。

有一条特殊通道要记住：标记为 UNKNOWN 的项不自动落入低风险层。不知道风险在哪，不能当成没风险。Phase 0 里有 9 条任务的图形界面必要性是 unknown，这 9 条不进自动低风险通道，工程风险和审核风险保持 UNKNOWN。

## 四道门

四道门是交付计数口径，也是放行顺序。任何一道不过，任务停在原地，不进下一道。

第一道，内容审核。专业真实性、契约完整性、资料可授权性、脱敏状态、重复风险。这一道由领域评审人和质量审核人负责。领域评审人不设专职岗位，从专家池里由系统自动派单。

第二道，工程转换。快照能不能转成目标格式，资产哈希对不对，目录和元数据齐不齐，版本是不是冻结版本。这一道由工程负责。

第三道，运行验证。构建、启动、执行、验证器、评分写入、产物收集，全部要有实际运行记录。这一道最容易出现"配置正确但没跑过"的假通过。

第四道，合作方验收。抽验、格式复核、复现测试。这一道由合作方判定。

## 评测要分七层做

不要一步跳到"跑一遍看分数"。按顺序加码，每层过了再进下一层。

1. 静态文件和 Schema 检查。
2. 环境构建和准备检查。
3. 验证器或评分器单独执行检查。
4. 单任务完整运行。
5. 重复运行和稳定性检查。
6. 批量运行，看失败率和资源占用。
7. 自动结果和人工复核对照。

评测记录不能只存一个分数。必须同时存：启动结果、完成结果、验证器状态、环境错误、超时、崩溃、评分误判、证据位置。只存分数的评测记录在争议时没有用。

## 六项已批准的机制

全量自动检查、专家自检、Agent 质量预审、风险分层人工审核、工程自动验证、项目负责人批次放行。这六项是已批准的机制，出处是 Phase 0 的决策记录。

没有冻结的是两个参数：抽样率和风险阈值。审核人数已由每批 22 名核心、评审副线和系统自动派单确定，不再单列。

## 评审怎么派单和校准

领域评审人不另招。专家主线生产、副线评审，系统按子域、利益冲突和当前负荷自动派单，规则写在 `docs/07-expert-supply.md` 的评审副线一节。

每批第 1 周用 3 条冻结样例校准尺度，前 10 条由领域负责人复核，之后随机 10% 双评。评审时限 5 个工作日，第 3 天提醒，第 5 天没完成就改派并降优先级。错误率高的评审人移出评审池，重新校准后才能回来。

派单不等于放水。评审人不是作者，作者不能评自己的任务，同一对专家不能连续互评，高风险任务派资深专家。工程复核和执业签字不进专家池，仍由工程和外部注册工程师做。

还有一条覆盖缺口要单独处理。3 条试点只覆盖商业会计、神经影像、建筑节能三个方向，首批 30 条里的企业分析、合规、经济社会研究没有试点样本。这三个子域的前 3 条任务全量人工复核，不按低风险层抽样放行；跑完前 3 条再回到常规分层。没有这条，3 条试点压出来的时间会把未验证的子域直接放量。

## Agent 能做什么，不能做什么

Agent 可以访谈、整理、检查、提示、生成建议。

Agent 不能决定五件事：任务是否真的具备业务价值、专业结果是否符合领域标准、资料是否有合法使用权、高风险的隐私与版权与安全问题是否可接受、验证器是否真的表达了任务目标。

所有 Agent 输出都要记录版本、来源、置信度和人工确认结果。Agent 的建议没有被专家确认，不算结论。

## 证据怎么写

项目里所有断言分五档标注：文档原文、代码行、命令输出、由证据推出的推断、没有证据。没有证据的事情不写实，没运行过的事情不写通过，引用不存在的来源等于没有证据。

这条规则看起来苛刻，但它是这个项目唯一能对抗"看起来做完了"的手段。Phase 0 的基线报告通篇没有出现"可以跑通"这类表述，全部停在 NOT_RUN，就是这条规则的结果。

## 什么时候可以进下一阶段

阶段 0 进阶段 1，条件是指标和边界明确，已经满足。

阶段 1 进阶段 2，条件是业务输入收敛。收敛的判据是阶段一的两个校验器全部通过，加上项目负责人签字。2026-11-11 项目负责人决定不做阶段一独立复审，签字改为自检。两个校验器全过，项目负责人已于 2026-11-11 签字。阶段 1 收口生效，可以进入阶段 2。这项例外的风险是阶段一证据没有第二个人独立复核，签字前要按阶段一入口文件的速查表抽验，并把抽验结果写进签字记录。

阶段 4 进阶段 5，条件是首批 30 条的链路能稳定重复且成本可接受。这一条没有任何替代方案，不能用"阶段 2 的 3 条试点通过"来替代 30 条的重复验证。

500 条交付前，最后一道是合作方验收。合作方说通过才算通过，内部认为通过不算。
