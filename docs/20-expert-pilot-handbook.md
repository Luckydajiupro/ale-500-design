# 专家试点手册

本文件面向参加 ALE 500 试点的专家，说明在现有平台里如何登录、建任务、填写任务源、上传资料、运行检查、提交、返修和确认 Agent 建议。本文件只写当前版本真实存在的页面、按钮和字段；设计稿里有、当前版本没有的功能，会明确写“当前版本不可用”，不按设想页面描述。本文件只讲内容、操作和记录，不涉及商务或结算安排。

试点的目的不是让专家熟悉一套已经定型的软件，而是用真实任务检验平台字段、检查规则和 Agent 建议是否可用。专家在操作中遇到的卡点、误报和不顺手之处，本身就是试点要收集的结果。

## 1. 项目目标与专家职责

本项目为 Agents' Last Exam（ALE）评测集生产 500 条原创专业工作任务。每条任务不是问答样本，而是一段可运行、可评测、可复现的专业工作：有真实资料、执行环境、多步操作、明确交付物和成功判定。官方已有的 122 条任务不计入 500，三条试点线也不计入 500。

专家交付的是一份规范任务源，包含十个块：任务身份、场景、资料、步骤、交付物、成功标准、环境、审核、来源、交接。平台把任务源保存为结构化数据，并在后续环节生成 ALE-data 包。专家不写 Dockerfile、不写 Verifier、不手工拼运行包，也不负责 Harbor 转换和正式评测。

专家在本试点中的职责。

- 按试点方向完成分配的任务实例，把真实专业工作拆成可观察、可复核的步骤。
- 提供可授权、可追溯的输入资料；合成资料明确标注，客户真实资料不进入试点。
- 写清交付物的相对路径、格式、结构和验收对应关系。
- 让每条成功标准都能被脚本、产物比对或人工评分表判定，权重合计为 100。
- 在平台里运行自动检查，处理阻断项，提交后按评审意见返修。
- 对 Agent 建议逐条接受、编辑或拒绝，并记录哪些建议不可用。
- 按试点记录模板报告实际用时、卡点和证据，不把组织参考工时当成个人考核。

专家不承担的事情。

- 不判断平台代码实现，不修改平台数据，不绕过状态机。
- 不代替领域评审人或质量审核人给自己的任务签字。
- 不承诺任务一定被 500 条正式生产接收；试点通过与否由试点出口判据决定。
- 不处理商务、合同、结算和采购事项。

任务组织参考工时只用于排期和资源准备。一条完整任务按 28 小时组织，平台辅助目标为 22 小时；这是任务级参考，不是个人工作量承诺，也不作为个人考核依据。

## 2. 试点范围与时间

试点从 2026-11-18 开始，到 2026-12-30 结束。三条方向并行推进，每条方向做 T1 人工基线与 T2 平台辅助两个实例，共 6 个任务实例。试点不覆盖全部 14 个域，也不承担 500 条的配额验证。

| 方向 | domain_code | 试点任务示例 |
|---|---|---|
| 商业 | business_finance | business_finance/accounting_reconcile_01 |
| 神经影像 | psychology_neuro | psychology_neuro/dicom_to_bids_01 |
| 建筑节能 | engineering | engineering/building_energy_baseline_01 |

周计划。

| 时间 | 工作 |
|---|---|
| 2026-11-18 至 11-21 | 签约、培训、范围冻结、账号与资料准备 |
| 2026-11-24 至 11-28 | T1 人工基线 |
| 2026-12-01 至 12-05 | T1 收尾与记录补齐 |
| 2026-12-08 至 12-12 | T2 平台辅助 |
| 2026-12-15 至 12-19 | T2 收尾、返修与证据补齐 |
| 2026-12-22 至 12-25 | 组包与校验 |
| 2026-12-28 至 12-30 | 试点收口 |

T1 与 T2 使用同一题族的不同实例，两个实例之间至少间隔 3 个工作日。T1 在平台外完成并记录人工过程；T2 在平台内完成，记录平台辅助后的实际用时、检查和返修。两条记录不能互相代替。

试点只使用公开数据或合成资料，不接触真实客户材料。资料授权按项目默认走法执行；需要新授权时先停该条试点，不先用后补。合成资料建议在文件名前加 `SYNTHETIC_` 前缀，这是 v0 操作约定，尚未冻结。

## 3. 登录与账号

试点账号由项目组发放，不使用公开演示账号承担正式试点记录。打开项目组给出的工作台地址，页面显示“登录专家工作台”，填写邮箱和密码，点击“登录”。

登录后的首页是“工作台”。顶栏左侧是“ALE 专家工作台”，中间有“工作台”；有评审权限的账号还会看到“评审队列”，有创建任务权限的账号会看到“新建任务”。右侧显示当前姓名、角色和“退出”按钮。

当前版本的行为。

- 登录会话有效期为 8 小时，过期后重新登录。
- 邮箱或密码错误时，页面返回“邮箱或密码不正确”，不提示账号是否存在。
- 账号被停用时不能登录，需要联系项目组恢复。
- 当前版本不提供自助修改密码、忘记密码、修改邮箱和多因素认证，这些功能当前版本不可用。
- 当前版本没有账号管理页面，新增账号、停用账号和角色变更由项目组在平台外处理。

演示环境预置了 expert、reviewer、quality、admin 等演示账号，只用于培训和走查，密码由培训组织者现场提供。正式试点记录必须使用个人账号，避免多人共用账号导致审计记录失真。

## 4. 创建任务

在“工作台”点击“新建任务”，进入“新建任务”页面。页面先建草稿，再进入结构化任务源表单。

需要填写的字段。

- 任务 ID：格式为 `domain/slug`，例如 `business_finance/accounting_reconcile_02`。必须包含一个斜杠，不能有空格，不能与已有任务重复。
- 一级领域：从 14 个域的下拉框中选择，必须与任务 ID 的前缀一致。
- 二级子域：默认 `accounting`，按任务实际子域填写，例如 `auditing`、`tax`。
- 中文标题：必填，写工作对象和动作，不写“练习”“测试”一类字样。
- 英文标题：建议填写，最终进入英文任务说明。
- 批次：试点默认 `w1-demo`，不要改成正式批次号。

点击“创建草稿”后，平台创建空任务源并跳到“编辑任务源”页面，页面提示“草稿已创建”。任务 ID、一级领域和二级子域创建后只读，当前版本不能修改。当前版本也没有删除任务的按钮，任务作废由项目组在平台外处理。

命名建议。

- slug 用小写英文和下划线，写清工作内容，例如 `accounting_reconcile`、`dicom_to_bids`、`building_energy_baseline`。
- 一个题族的变体用 `_01`、`_02` 后缀，不把客户名、项目代号写进任务 ID。
- 中文标题和英文标题指向同一条工作，不要一个写对账、一个写报表分析。

## 5. 填写任务源十块

“编辑任务源”页面把十个块合并成八张卡片。任务身份、场景、资料、操作步骤、交付物、成功标准、环境各占一张卡片，审核、来源与交接合并在第八张。字段名沿用英文 canonical 名称，页面显示中文标签。

| 任务源块 | 页面位置 | 平台处理方式 |
|---|---|---|
| 任务身份 | 第 1 张卡片 | 任务 ID、领域、子域只读；其余手填 |
| 场景 | 第 2 张卡片 | 全部手填 |
| 资料 | 第 3 张卡片 | 只读表；文件在任务详情页上传 |
| 步骤 | 第 4 张卡片 | 逐行手填 |
| 交付物 | 第 5 张卡片 | 逐行手填 |
| 成功标准 | 第 6 张卡片 | 逐行手填 |
| 环境 | 第 7 张卡片 | 手填并选择枚举 |
| 审核 | 第 8 张卡片 | 风险等级、风险理由、所需评审 |
| 来源 | 第 8 张卡片 | 来源行；作者类型和原创声明由平台写入 |
| 交接 | 第 8 张卡片 | 已知缺口和保密确认；目标格式由平台写入 |

任务源正文建议用英文写，字段名保持英文，标题和解释可以中文。当前表单没有独立的“任务说明”富文本框，英文任务说明由场景、步骤、交付物和成功标准这些字段共同承载，所以每个字段都要写成完整、可读的英文句子。

### 5.1 任务身份

第 1 张卡片“任务身份”包含以下内容。

- 任务 ID：只读，创建时确定。
- 批次：默认 `w1-demo`，试点不改。
- 一级领域：只读，创建时确定。
- 二级子域：只读，创建时确定。
- 中文标题：必填，写清组织情境中的具体工作对象。
- 英文标题：建议填写，使用名词短语，不用问句。
- 语言：`en` 或 `zh`。试点任务源正文用英文时选 `en`。
- 难度理由：必填。写清为什么这条任务需要专业判断、多步操作或工具使用，不要只写“较难”“需要经验”。

难度理由要能解释任务复杂度来自哪里，例如资料冲突、口径选择、异常分类、跨表核对或专业规范适用。只写“需要仔细”不算理由。

### 5.2 场景与专业判断

第 2 张卡片要求写清工作为什么发生、谁在做、做给谁看、边界在哪里。

- 角色：具体岗位，例如“Staff accountant”“Clinical data manager”，不写“专业人士”“专家”。
- 触发原因：什么事件让这项工作现在必须做，例如月末结账、监管报送、项目评审。
- 受众：交付物给谁看，例如财务经理、审计师、研究负责人。
- 真实工作证据：访谈、流程记录、公开规范或岗位职责的来源说明。
- 组织情境：组织类型、业务背景、当前状态和已知约束。
- 约束：每行一条，至少写 2 条。平台在空填时会补一条默认值，专家必须自己覆盖，不能依赖默认值。
- 不做什么：每行一条，至少 1 条。写清禁止的外部查询、禁止的改动和不在范围内的判断。
- 专业判断点：通过约束、异常处理和成功标准体现，当前表单没有单独的“判断点”输入框。

约束要写成可执行条件，例如“只能使用 input/ 下的文件”“金额保留两位小数”“不得修改源数据行”。不要写“保证准确”“符合专业标准”这类无法检查的话。

### 5.3 资料

第 3 张卡片只展示已经挂到任务源的资料，表头是 ID、角色、路径、许可、PII、大小。表单里不能新增资料，也不能手填哈希。正确顺序是先保存草稿，再到任务详情页上传。

任务详情页的“资料与上传”区域在任务可编辑时显示“上传一份资料”。展开后填写以下字段。

- material_id：留空时平台按全库计数自动生成 `M-001` 形式；也可以手填，但同一任务内不能重复。
- 文件：选择本地文件，单个文件不能超过 20 MiB。
- kind：`document`、`dataset`、`code`、`image` 四选一。
- role：`input`、`reference`、`template` 三选一。至少一份 `input`；`reference` 是答案或评分依据，不进入被评 Agent 的可见输入。
- layer：`raw`、`deidentified`、`work`、`reference`。role 选 `reference` 时平台强制 layer 为 `reference`。
- license_type：`synthetic`、`public_domain`、`cc_by`、`proprietary`、`internal` 五选一。平台当前把再分发标记固定为允许，所以不要上传不允许再分发的资料。
- pii_level：`none`、`low`、`medium`、`high`。高危 PII 会被自动检查阻断，不能在试点提交。

点击“上传并挂到任务源”后，平台保存文件、计算 SHA-256、记录字节数，并把资料条目写回任务源。专家不需要也不应该手填哈希；自动检查会把任务源记录的哈希与资料库最新版本比对。

资料设计的硬要求。

- 至少一份真实来源文件或明确标注的合成件。合成件在文件名前加 `SYNTHETIC_`，并在说明里写“合成演示资料，不含真实客户数据”。
- 答案、评分脚本和隐藏测试放 `reference`，不要放 `input`。
- 图片、表格和代码都要有可打开的工具和格式说明；不要依赖专家本机才有的文件。
- 许可不明、来源打不开、需要登录才能访问的资料不要上传。

当前版本不提供资料删除按钮，也不提供替换文件的独立按钮。重复上传同一 material_id 会追加一个新版本；删除或更正资料需要走支持渠道，由项目组在平台外处理。

### 5.4 操作步骤

第 4 张卡片“操作步骤”是一张可增行的表，列是 #、动作、工具、输入、预期状态、检查点、分钟。

- #：步骤号，从 1 开始连续编号，至少 3 步。
- 动作：一句可执行的英文动作，写清对象和操作，例如“Normalize posting dates to ISO format”。
- 工具：真实工具和版本，例如“Python 3.11 with pandas 2.1.4”“LibreOffice Calc 7.6”。不要写“专业软件”“公司系统”。
- 输入：用逗号分隔的 material_id 或上一步产物路径，例如 `M-001,M-002`。
- 预期状态：完成后可观察的结果，例如“120 rows parsed, zero invalid dates”。不要写“理解资料”“处理完成”。
- 检查点：至少勾选 1 个，通常放在资料核对、匹配完成和交付物生成之后。
- 分钟：该步骤的组织参考用时，不是个人考核。

步骤之间要有依赖关系。每一步的输入要么是上传的资料，要么是前面步骤的产物；不要出现“直接得出结论”的跳跃。工具必须能在声明的离线环境里运行，不能写“运行期下载”“最新版”。

### 5.5 交付物

第 5 张卡片“交付物”的列是 ID、路径、格式、说明、步骤、验收标准。

- ID：`D-001` 形式，任务内唯一。
- 路径：相对路径，以 `output/` 开头，例如 `output/reconciliation_report.md`。不能写绝对路径，不能写 `../`。
- 格式：从下拉框选择，常用 `md`、`csv`、`json`、`xlsx`、`docx`、`pdf`、`py`。
- 说明：写清文件里必须有哪些内容、哪些列、哪些小节。
- 步骤：产出该文件的步骤号，必须指向真实存在的步骤。
- 验收标准：填成功标准的 ID，多个用逗号分隔，例如 `C-001,C-002`。

当前版本把所有交付物都按必交处理，页面没有“是否必交”的勾选框。至少要有 1 个交付物。交付物的路径要和任务说明、成功标准、交接里的文件清单逐字一致。

### 5.6 成功标准

第 6 张卡片“成功标准”的列是 ID、维度、检查方式、权重、阈值、证据、关键。

- ID：`C-001` 形式，任务内唯一。
- 维度：`correctness`、`completeness`、`format`、`professional_judgment`、`process` 五选一。
- 检查方式：`auto_script`、`artifact_diff`、`llm_judge`、`human_rubric` 四选一。
- 权重：整数，所有标准合计必须等于 100。平台会阻断不等于 100 的任务源。
- 阈值：写可判定的条件，例如“117 matched pairs and 5 exception rows”“report contains all six required sections”。不要写“合理”“基本正确”“适当”。
- 证据：判定时要看哪些文件、日志或截图。
- 关键：至少勾选 1 条。关键标准不通过时，任务不能进入通过状态。

`auto_script` 和 `artifact_diff` 必须能在工程侧实现检查；`llm_judge` 和 `human_rubric` 必须给出评分维度、等级和判分边界。当前表单有隐藏的 `verifier_hint` 字段，平台会填默认说明，专家不需要在页面上编辑。维度要覆盖正确性、完整性、格式和至少一个专业判断点，不能只考文件是否存在。

### 5.7 环境与资源

第 7 张卡片包含以下字段。

- OS：`linux` 或 `windows`。
- OS 版本：写具体版本，例如 `Ubuntu 22.04`。
- GUI：`no` 或 `yes`。试点默认 `no`；需要图形界面时写清理由，并预期当前版本不能自动判定 GUI 操作。
- CPU、RAM GB、磁盘 GB、时限分钟：按任务实际需要填写，默认 2 核、4 GB、20 GB、60 分钟。
- 网络：`none`、`staged-local`、`public-ref`、`online-required`。试点默认 `none`；任何在线依赖都要在理由里说明，并会被重点审核。当前版本不提供在线运行环境。
- 网络理由：选择非 `none` 时必填。
- 软件：每行 `name|version|license|install`，例如 `Python|3.11.8|PSF-2.0|preinstalled`。
- 需要 GPU：默认不勾选。

软件不能写 `latest`，不能依赖运行期下载，不能依赖专家本机已装但镜像里没有的包。空填时平台会补 `LibreOffice 7.6`，这只是默认值，不代表任务真的需要它，专家必须按实际环境覆盖。

### 5.8 审核、来源与交接

第 8 张卡片把三个块放在一起。

- 风险等级：`low`、`medium`、`high`、`unknown`。有未脱敏 PII、在线服务、GUI 不可判定、专有软件、执业签字或高风险领域时，不能填 `low`。
- 风险理由：写清风险来自数据、工具、判断还是外部依赖。
- 所需评审：每行 `role:count`，默认 `domain_reviewer:1` 和 `quality_reviewer:1`。试点不要减少评审角色。
- 来源：每行 `source_id|url_or_path`。合成资料可以写 `S-001|synthetic://...`；公开资料写真实可打开的地址。
- 已知缺口：写清当前版本无法覆盖的文件类型、工具、外部服务或判断边界。
- 保密确认：勾选“我确认任务源与资料不含未授权秘密或客户数据”。不勾选时任务源不能提交。

作者类型、原创声明、目标格式、目标 schema 版本和期望文件清单由平台写入，专家不需要在页面上填写。目标格式是 `ale_task_toml`，目标 schema 是 `1.4+ale.1`。

## 6. 保存草稿

填写过程中随时点击页面底部的“保存草稿”。保存成功后停留在编辑页，任务状态仍为 `draft` 或 `returned`，不会生成不可变版本。页面顶部的说明是“保存草稿不会冻结版本。提交后才生成不可变版本。”

保存时的实际规则。

- 只有 `draft` 和 `returned` 状态可以编辑；已提交、审核中、已冻结和已入库的任务不能编辑。
- 平台用隐藏的 `expected_lock_version` 做并发保护。两个页面同时编辑时，后保存的会报版本冲突，错误码是 `LOCK_VERSION_CONFLICT`，需要刷新后重新填写改动。
- 保存不会校验全部字段，缺字段也能先存草稿；真正的阻断在“运行检查”和“提交审核”时出现。
- “取消”只返回任务详情，不保存当前改动。
- 当前版本没有自动保存、离线草稿和草稿导出，这些功能当前版本不可用。

建议每完成一张卡片保存一次，上传资料前先保存，避免表单里的旧值覆盖刚上传的资料条目。

## 7. 运行自动检查

保存草稿后进入任务详情页，点击“运行检查”。检查结果显示在“自动检查”卡片，列是检查、结果、级别、字段、说明、时间。没有跑过检查时，卡片显示“还没有运行检查”。

当前版本真正给出结论的检查。

- 结构与必填项：十块是否存在、必填字段是否为空、语言和资料枚举是否合法、任务 ID 是否为 `domain/slug`。
- 成功标准：至少一条标准、权重合计是否为 100、是否至少有一条关键标准、阈值是否为空或写成“合理/适当/reasonable”。
- 交付物与步骤：至少一个交付物、交付物是否有路径和格式、步骤是否少于 3 步。
- 环境与网络：网络模式是否为平台禁止的在线模式。
- 资料资产：任务源引用的资料是否存在、是否上传过版本、任务源记录的 SHA-256 是否与资料库最新版本一致。
- PII 申报：PII 等级是否合法，`high` 是否触发阻断。

以下检查当前版本不可用，平台只用 `info` 级行提示“未在骨架内实现”，不能把这些行当成通过结论。

- 重复与高度相似检查：`ACHK_DUPLICATE`，当前版本不可用。
- 环境与软件依赖检查：`ACHK_ENV_OFFLINE`，当前版本不可用。
- ALE-data 包生成预检：`ACHK_PACKAGE_DRY_RUN`，当前版本不可用。
- lint、prepare、validate 与冒烟：`ACHK_LINT`，当前版本不可用。
- 文本字段一致性检查和资料内容敏感信息扫描没有独立检查项，平台不会替专家判断描述是否自相矛盾、文件里是否含个人信息。
- ALE-data 包在管理员执行“自动组包”后生成，不在专家自动检查页生成。

阻断项会以 `blocker` 级别显示，常见错误码有 `SCHEMA_FIELD_REQUIRED`、`SCHEMA_WEIGHT_SUM`、`SCHEMA_CRITICAL_MISSING`、`SCHEMA_STEPS_MIN`、`SCHEMA_MATERIAL_UNKNOWN`、`ACHK_MATERIAL_MISSING`、`ACHK_MATERIAL_NO_BYTES`、`ACHK_MATERIAL_HASH`。有阻断项时页面提示“自动检查有 N 个阻断项”，不能提交。

自动检查通过只说明结构和引用没有硬错误，不说明任务专业上成立。提交前仍要完成本文件给出的人工检查清单。

## 8. 提交审核

自动检查没有阻断项后，在任务详情页点击“提交审核”。平台会再跑一次检查，然后生成不可变版本并进入 `auto_checked`，页面提示“已提交，进入自动检查与领域评审”。提交后任务源和资料条目只读，专家不能再改。

提交时发生的事。

- 平台生成 `v1` 或下一个版本号，记录任务源哈希。
- 平台自动创建一条领域评审，类型为 `domain`，轮次为第 1 轮，SLA 为 5 个工作日。
- 任务出现在领域评审人的“评审队列”里，专家不需要自己派单。
- 提交不会通知项目组以外的人；当前版本没有站内信或邮件提醒，专家要在“工作台”看状态变化。

如果提交时仍有阻断项，页面提示“任务源存在阻断项，不能提交”，并列出阻断项，不会生成版本。处理完阻断项后重新运行检查，再提交。

## 9. 领域评审退回与返修

领域评审人在“评审队列”领取任务，打开评审页，填写问题项并选择“通过”或“退回返修”。问题项每行至少四段，用竖线分隔：维度、字段、级别、说明，例如 `correctness|success_criteria[0].threshold|blocker|阈值无法判定`。

退回后任务状态变为 `returned`，专家重新获得编辑权限。返修时要做的事。

- 在“工作台”找到状态为 `returned` 的任务，打开任务详情，点击“编辑任务源”。
- 逐条读问题项，按字段定位修改；不要只改文字说明而不改实际字段。
- 修改后保存草稿，重新“运行检查”，确认阻断项清零。
- 再次“提交审核”，平台生成新版本，例如 `v2`，并创建下一轮领域评审。

返修规则。

- 常规评审 SLA 是 5 个工作日，首批任务按 3 个工作日组织；这是评审时限，不是专家返修时限。
- 默认允许两轮返修；逾期或两轮仍未解决时，项目组可以改派或缩范围。
- 阻断项只能通过返修、拒收或升级处理，不能“通过但备注”。
- 专家不能评审自己的任务，也不能与同一评审人连续互评。
- 当前版本没有“评审意见回复”输入框，返修说明写在任务源相应字段或“已知缺口”里；需要补充解释时走支持渠道。

领域评审通过后，任务不会直接进入 `approved`，而是自动进入质量审核。专家在这一步通常不需要操作，等待质量审核结果。

## 10. 质量审核

质量审核人从“评审队列”领取 `quality` 类型评审，检查专业真实性、任务契约一致、资料可授权、交付物可验证、难度与工作量、重复与泄漏六个维度。质量审核可以选择“通过”或“退回返修”。

质量审核通过后任务进入 `approved`，专家侧编辑权限关闭。质量审核退回时任务回到 `returned`，返修流程与领域评审退回相同，仍然要重新检查、重新提交并生成新版本。

质量审核关注的是整条任务能否作为评测样本，不只是文字是否通顺。常见退回原因包括交付物无法由步骤产出、成功标准测不到专业判断、资料许可与来源不一致、任务与已有样本高度相似。当前版本没有自动相似度检查，这类问题主要靠人工判断。

## 11. 版本记录

任务详情页的“审核与版本”卡片显示评审记录和版本记录。版本行包含版本号、生成时间和任务源哈希前 12 位，例如 `v2 · 2026-12-10 14:22 · fda685eb60c4`。提交一次生成一个版本，保存草稿不生成版本。

审核通过后，管理员可以执行“冻结快照”“自动组包”“L1–L5 校验”“幂等入库”。这些按钮只对管理员和相应状态显示，专家看不到也不应操作。

- 冻结后任务源不可再改，快照不可覆盖。
- 组包生成 ALE-data 包，包内包含 `PACKAGE.json`、清单、资料、来源、交接、校验报告和 `base/` 目录。
- L1–L5 校验覆盖结构、语义、完整性、安全和入库冲突。
- 入库写入回执，记录包哈希、校验报告哈希、接收时间和接收人。

当前版本没有版本差异对比页面，也没有导出任务源、导出审核记录和批量下载，这些功能当前版本不可用。需要对比两个版本时，记录版本号和哈希，通过支持渠道申请后台导出。

## 12. Agent 建议的接受、修改与拒绝

任务详情页有“Agent 建议”卡片和“生成结构化建议”按钮，只在任务可编辑时显示。点击后平台生成若干条建议，页面提示“已生成 N 条建议，等待逐条确认”。

建议表的列是字段、建议值、置信度、状态、确认。状态为 `proposed` 时，每条建议有三个动作。

- 接受：直接采用建议值，状态变为 `accepted`。
- 编辑后接受：在“可编辑后接受”输入框里改成自己的值，再提交，状态变为 `edited`。
- 拒绝：保留原值，状态变为 `rejected`。

实际规则。

- 建议只写入建议表，不会自动改任务源；只有专家确认后才可能写回。
- 自动采纳必须为 0。平台没有“全部接受”按钮，也不允许跳过逐条确认。
- 已处理的建议不能再次处理，重复操作会返回 `SUGGESTION_CLOSED`。
- 当前版本的 Agent 建议是规则式占位，不调用真实模型；五项能力中只做了结构化建议和逐字段确认，访谈、追问、预检和审核辅助没有完整实现，这些能力当前版本不可用。
- 建议可能提出字段值、缺失项或表述改写，但不保证专业正确。专家必须逐条核对，不能把置信度当质量结论。

试点要记录每条建议的去向和理由，尤其是拒绝和编辑的原因。这些记录用于判断 Agent 是否真的节省时间，而不是只看生成了多少条建议。

## 13. 常见错误

| 现象 | 常见原因 | 处理方式 |
|---|---|---|
| 创建任务报任务 ID 非法 | 没有斜杠、含空格或与已有任务重复 | 改成 `domain/slug`，换一个 slug |
| 保存后资料表是空的 | 只在表单里看资料，没有到任务详情页上传 | 先保存草稿，再到“资料与上传”上传 |
| 上传报“单个文件不能超过 20 MiB” | 文件过大 | 压缩、拆分或改用更小的合成资料 |
| 自动检查报 `SCHEMA_WEIGHT_SUM` | 标准权重合计不等于 100 | 调整整数权重，确保合计正好 100 |
| 自动检查报 `SCHEMA_CRITICAL_MISSING` | 没有勾选关键标准 | 至少勾选一条真正决定成败的标准 |
| 自动检查报 `SCHEMA_STEPS_MIN` | 步骤少于 3 步 | 拆出资料核对、处理和交付物生成步骤 |
| 自动检查报 `SCHEMA_FIELD_REQUIRED` | 必填字段为空 | 按字段路径补齐，不要只改标题 |
| 自动检查报 `ACHK_MATERIAL_MISSING` | 任务源引用了资料库没有的 ID | 重新上传正确资料并让平台重新挂接，或联系项目组处理错误引用 |
| 自动检查报 `ACHK_MATERIAL_HASH` | 任务源哈希与最新上传版本不一致 | 重新上传同一 material_id，或让平台重新挂接 |
| 提交报“任务源存在阻断项” | 检查未通过 | 先运行检查，处理全部 blocker |
| 提交后不能编辑 | 任务已生成版本，状态为 `auto_checked` 或之后 | 等评审退回，或联系项目组 |
| 返修后仍是旧内容 | 改了表单但没重新提交，或浏览器里是旧页面 | 刷新、重新保存、重新检查、重新提交 |
| Agent 建议不能再次处理 | 建议已被接受、编辑或拒绝 | 刷新页面，查看状态 |
| 登录后看不到“新建任务” | 账号没有 `task:create` 权限 | 联系项目组确认角色 |

## 14. 资料保密与删除

试点只使用公开数据或合成资料，不接触真实客户材料。以下内容不能上传。

- 客户合同、发票、银行流水、病历、员工记录和未公开的经营数据。
- 可以直接识别个人身份的姓名、证件号、联系方式、住址和照片。
- 未脱敏的高危 PII。平台会把 `high` 级别的 PII 作为阻断项，任务不能提交。
- 商业秘密、内部口令、密钥、访问令牌和未授权的第三方材料。
- 答案、评分脚本和隐藏测试不能放在 `input`，只能放 `reference`。

资料授权的基本判断。

- 公共领域、CC0、CC-BY、MIT、Apache-2.0、BSD 和开放政府数据可以用，但要保留来源和许可说明。
- CC-BY-NC 按 v0 不用于商业评测。
- 许可不明、来源打不开、需要登录或受限制才能访问的资料，按不可用处理。
- 合成资料要标注合成，文件名加 `SYNTHETIC_` 前缀，说明里写清“不含真实客户数据”。

平台把上传文件按内容哈希存储，记录上传人、时间、字节数和 SHA-256；审计日志追加写，记录操作者、动作、对象和状态变化。被评 Agent 只能看到 `base/input` 和 `base/software`，看不到 `reference`、`PACKAGE.json`、校验报告和回执。

当前版本不提供资料删除、任务删除和自助撤回，这些功能当前版本不可用。需要删除时，向支持渠道提交任务 ID、material_id、文件名和删除理由，由项目组在平台外处理并记录。试点退出后的资料删除按项目约定执行；“退出后 30 天删除确认”是 v0 假设，尚未批准，不能当作已经生效的承诺。

## 15. 支持渠道

当前版本没有平台工单页面、在线客服和帮助中心，这些功能当前版本不可用。试点期间使用项目组在培训时指定的书面渠道，通常是试点联络人的邮箱或项目协作空间。

提交问题时请附上以下信息。

- 账号邮箱和角色。
- 任务 ID 和当前状态，例如 `business_finance/accounting_reconcile_01`、`returned`。
- 出错页面的按钮或操作名称。
- 错误码和完整提示，例如 `LOCK_VERSION_CONFLICT`、`SUBMIT_BLOCKED`。
- 复现步骤、发生时间和截图。
- 涉及资料时附 material_id，不要直接贴客户数据或个人信息。

响应时限。“平台工单 + 2 个工作日响应”是 v0 假设，尚未批准；试点期间按培训时确认的实际渠道和时限执行。涉及账号停用、资料删除、许可边界和 PII 的问题优先升级给项目组，不在平台里自行处理。

支持渠道只处理操作、账号、资料和流程问题，不处理商务和结算事项。

## 16. 提交前人工检查清单

自动检查通过后，逐项确认以下内容，再点“提交审核”。

- 任务 ID 是 `domain/slug`，领域、子域和标题指向同一条工作。
- 中文标题具体，英文标题不是问句，难度理由写了复杂度来源。
- 场景有具体角色、组织情境、触发事件和受众，不是泛化描述。
- 约束至少 2 条，禁止范围至少 1 条，都是可执行条件。
- 至少一份 `input` 资料，合成件已标注，许可和 PII 等级填写正确。
- 答案和评分依据在 `reference`，没有出现在 `input`。
- 步骤至少 3 步、连续编号、至少 1 个检查点，工具和版本可离线运行。
- 每个交付物有相对路径、格式、说明和产出步骤，路径没有 `../` 和绝对路径。
- 交付物路径与成功标准、交接里的文件清单逐字一致。
- 成功标准权重合计 100，至少 1 条关键标准，阈值可判定。
- 至少一条标准考专业判断，不是只考文件存在或格式。
- 环境 OS、版本、软件、网络和资源写清，没有 `latest` 和运行期下载。
- 风险等级与资料、工具、判断相匹配，没有把高风险任务填成 `low`。
- 来源可打开或可追溯，已知缺口写清，保密确认已勾选。
- 自动检查的阻断项为 0，跳过的检查没有被当成通过。
- Agent 建议逐条处理完，没有未确认的建议。
- 记录实际用时、卡点和证据，准备填写 T1 或 T2 记录模板。
